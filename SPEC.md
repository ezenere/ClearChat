# ClearChat — Spec / Contrato

App desktop **Electron** (electron-vite + React + TypeScript + Tailwind v4 + zustand + lucide-react).
UI em **pt-BR**. Chat com IA via qualquer endpoint **OpenAI-compatible** (`POST {baseUrl}/chat/completions`, SSE streaming). Padrão: OpenRouter (`https://openrouter.ai/api/v1`).

Princípio: **minimalismo + controle total**. Criar chat → escolher modelo + system prompt + **diretório raiz** (workspace) → conversar. Tudo que vai para a API como parte do prompt aparece na UI com um ícone **(i)** com tooltip explicando exatamente o que é enviado e como (ex.: "Enviado como mensagem `role: system`", "Enviado no campo `tools` da request", "Anexado ao final do system prompt").

## Layout de pastas

```
src/
  shared/      types.ts, ipc.ts (canais + interface ClearApi), defaults.ts (textos/config padrão), tools.ts (definições das tools)   ← contrato
  main/        index.ts (janela), db.ts, migrate.ts (dados do nome antigo), ipc.ts (handlers), agent/ (runner, llm, request, queue, approvals), tools/
  preload/     index.ts (contextBridge → window.api)
  renderer/    React app
```

Segurança Electron: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: false` só se preciso para preload. Toda lógica de rede, tools e DB fica no **main process**.

IDs: `crypto.randomUUID()` (exceto memórias: `m` + 7 caracteres base36 — ver "Memória"). Timestamps: `Date.now()`. Deletar chat apaga sessions/messages (cascade manual ou FK ON DELETE CASCADE).

**Migração do nome antigo** (`src/main/migrate.ts`, `migrateLegacyData(userData)`): o app se chamava "CleartChat" (typo). No `ready`, antes de abrir o banco e só no userData padrão (não com `CLEARCHAT_USER_DATA`): se `<userData>/clearchat.db` não existe e `<irmão>/CleartChat/cleartchat.db` existe, copia com `VACUUM INTO` numa conexão somente leitura (cópia consistente, já com o WAL) para um temporário e renomeia; fallback: cópia crua de `.db` + `-wal`/`-shm` validada ao abrir. O diretório antigo fica intacto. Testado em `e2e/unit.test.ts`.

## Construção da request (`src/main/agent/request.ts` — função pura `buildRequest(chat, session, history, provider)`, usada pelo runner E pelo preview)

```
body = {
  model: session.model,
  messages: [ systemMessage, ...activeHistory(history).map(m => m.message) ],   // a partir da fronteira de compactação mais recente
  stream: true, stream_options: { include_usage: true },
  tools?: (nativeTools && toolsDisponiveis.length) ? definicoes : omitido,
  ...params definidos E aceitos pelo modelo (ver "Parâmetros por modelo"; reasoning_effort → OpenRouter: reasoning:{effort}; outros: reasoning_effort),
  usage: { include: true }   // só se baseUrl contém openrouter.ai
  ...JSON.parse(extraBody)   // por último
}
system content = (session.depth===0 ? systemPrompt : subagentSystemPrompt)
               + (envInPrompt ? "\n\n<environment>\nroot: …\nos: …\nshell: zsh 5.9\n<regras do workspace>\n</environment>" : "")   // SEM data/hora nem dir. atual do shell → estável p/ cache
               + (memória ativa e principal ? "\n\n" + índice + "\n\n" + help : "")          // ver "Memória"
               + (skills ativas e supportPrompt.enabled ? "\n\n" + (supportPrompt.text ?? DEFAULT_SKILLS_SUPPORT_PROMPT) : "")   // ver "Skills"
               + (toolsInPrompt ? "\n\n" + (toolsPromptText ?? defaultToolsPrompt(tools, nativeTools)) : "")
```
Se o system content ficar vazio, não envia mensagem system.
Bloco de ambiente (`environmentBlock(cfg, env)`): `root: <cwd>`, `os`, `shell`, a linha "Diretório raiz (workspace) desta sessão: root acima. Caminhos relativos nas ferramentas resolvem a partir dele e o bash começa nele (o diretório do shell persiste entre chamadas)." + (confineToRoot) "As ferramentas de arquivo só acessam caminhos dentro do diretório raiz." + (sandboxBash e bwrap instalado) "O bash roda em sandbox: só o diretório raiz (e um /tmp privado) é gravável.".
Headers (adaptadores openai/openrouter; Anthropic nativa: ver "Adaptadores de provider"): `Content-Type`, `Authorization: Bearer <key>`, + headers da **assinatura de app** do chat (ver abaixo; qualquer provider) e por último `provider.headers` (sobrescrevem).

**Token caching**: o histórico é imutável e reenviado exatamente como persistido; nada dinâmico no prefixo. Se `cacheEnabled`: (1) system vira `[{type:"text", text, cache_control:{type:"ephemeral"}}]`; (2) a **última mensagem do array (qualquer role, inclusive `tool`)** tem seu último text part marcado com `cache_control` (se não tiver texto, recua até a anterior que tenha); (3) a última mensagem `user`, se for outra, também (máx. 3 breakpoints; Anthropic aceita 4). Conversão string → parts **apenas na cópia enviada**, não no DB. Mensagens `meta.kind: "error"` (erros persistidos só para exibição) são excluídas da request. Ordem fixa: tools → system → histórico. Mostrar `cachedTokens` no rodapé de uso de cada resposta. Parse do usage: `usage.prompt_tokens_details.cached_tokens`, `usage.prompt_tokens_details.cache_write_tokens` (se houver), `usage.completion_tokens_details.reasoning_tokens`, `usage.cost` (OpenRouter).

Streaming: SSE `data: {...}` com `choices[0].delta.{content, reasoning | reasoning_content, tool_calls[]}`; acumular tool_calls por `index`. Ignorar linhas `: OPENROUTER PROCESSING`. `[DONE]` encerra. Erros HTTP → mensagem de erro legível (body da resposta) como evento `error` + session status `error` + mensagem persistida só para exibição (`{role:'assistant', content: erro}`, `meta: {kind:'error', synthetic:true, error}`) — sobrevive ao reinício e **nunca** vai para a API (`buildRequest` a exclui). Regenerate/apagar a mensagem (tool com `meta.subSessionId` ou assistant com o tool_call) de um `delegate_task` apaga a subsessão (e descendentes) e emite `session-deleted`.

**Modo sem tools nativas** (`nativeTools=false` e tools habilitadas): o texto padrão de tools no prompt instrui o modelo a chamar tools com `<tool_call>{"name": "...", "arguments": {...}}</tool_call>`. O runner faz parse disso no texto final do assistente; o resultado volta como mensagem `user` sintética: `<tool_result name="...">…</tool_result>` (meta.synthetic, kind `tool-result-text` pode ser derivado do conteúdo). ### Assinatura de app (`src/shared/appSignatures.ts`)

Por chat, o usuário escolhe quais headers de atribuição (`HTTP-Referer` / `X-Title`) vão em cada request — controle total, para qualquer provider (não só OpenRouter).
- `ChatConfig.appSignature: string` (id de `APP_SIGNATURES`; padrão `DEFAULT_APP_SIGNATURE = 'clearchat'`; chats antigos sem o campo = `'clearchat'`; o id antigo `'cleartchat'` é um alias silencioso — `normalizeAppSignatureId` o resolve para `'clearchat'` ao ler o chat, no seletor e em `resolveAppSignatureHeaders`) e `ChatConfig.appSignatureCustom?: { referer: string; title: string }` (usado quando `appSignature === 'custom'`).
- `APP_SIGNATURES: AppSignature[]` (`{ id, label, referer?, title? }`): `none` (Nenhuma — não envia headers de atribuição), `clearchat` (padrão), `cline`, `roo-code`, `kilo-code`, `aider`, `opencode`, `sillytavern`, `open-webui`, `librechat` (valores conferidos no código-fonte de cada app) e `custom` (Personalizada).
- `resolveAppSignatureHeaders(id, custom?)` → `{ 'HTTP-Referer'?, 'X-Title'? }` (campos vazios são omitidos; id desconhecido → ClearChat). `buildRequest` aplica depois de `Authorization` e antes de `provider.headers`; o `previewRequest` mostra os headers; subsessões usam a assinatura do chat.

### Personas (presets de chat) — `src/shared/presets.ts`

Registro de configurações de chat reutilizáveis (tabela `presets`, `presetsRepo` em `repo.ts`, canais `presets:*`).
- `config` é um **snapshot parcial** de `ChatConfig` com só os campos de `PRESET_FIELDS`: `providerId`, `model`, `systemPrompt`, `params`, `enabledTools`, `nativeTools`, `toolsInPrompt`, `toolsPromptText`, `envInPrompt`, `cacheEnabled`, `subagentSystemPrompt`, `approvalModes` (o override por chat; as listas são globais e nunca entram), `smartApprove`, `appSignature`, `appSignatureCustom`, `contextWindow`, `compactThreshold`, `autoCompact`, `compactPrompt`, `maxToolOutputChars`, `confineToRoot`, `sandboxBash`, `smartApprove`, `memory`, `skills` (os dois gravados normalizados) — e `cwd` só se o usuário marcar "Incluir diretório raiz" (desligado por padrão). `presetId`, título e chaves desconhecidas nunca entram (`sanitizePresetConfig`, aplicado no main ao salvar e ao ler).
- **Campos ausentes seguem os padrões** de "Novos chats" (modelo/system prompt/pasta padrão + `DEFAULT_CHAT_CONFIG`): `applyPreset(base, config)` = base ← persona (params mesclados). `providerId` + `model` são **um par** (`resolvePresetModel` em `src/shared/models.ts`): persona sem modelo → o par padrão (o `providerId` sozinho é ignorado); com modelo e sem `providerId` (antigas) → o modelo no provedor padrão; provedor apagado → o par padrão + aviso no Novo chat e no editor ("O provedor … não existe mais"). Sem `cacheEnabled` na persona → segue o provedor (OpenRouter liga).
- `snapshotPreset(chatConfig, { includeCwd })` = persona a partir de um chat (snapshot completo dos campos acima). `patchPresetConfig` mescla edições num rascunho (params nulos removem).
- **Primeira execução** (`presetsRepo.seed()`, chamado em `registerIpc`): cria "Padrão" com config **vazia** (= segue "Novos chats", então mudar o modelo/system prompt padrão continua valendo) e a define em `defaultPresetId`; a flag `presetsSeeded` impede recriá-la depois de apagada. Sem nenhuma persona o app funciona igual (só os padrões).
- Apagar a persona padrão limpa `defaultPresetId`. `duplicate` cria "Nome (cópia)". Chats guardam `config.presetId` (informativo: apagar/editar a persona não muda chats existentes).
- Tudo o que uma persona define são os mesmos campos do chat, com os mesmos (i) (system prompt, params, tools…), nos mesmos editores.

## Adaptadores de provider (`src/main/agent/adapters/`, `src/shared/providerKinds.ts`)

`Provider.kind` (`'openai' | 'openrouter' | 'anthropic'`; ausente → inferido pela URL com `providerKind()`) escolhe o adaptador. `adapterFor(kind)` dá o transporte (`chatUrl`, `headers`, `getHeaders`); `buildRequest`/`streamChat`/`listModels` continuam as fachadas usadas por runner, compactação, Smart-Approve (`buildJudgeRequest`) e preview. `BuiltRequest.kind` diz o formato do body/stream (ausente = OpenAI).
- **openai** (genérico): `POST {baseUrl}/chat/completions`, `Authorization: Bearer`, `reasoning_effort` plano, sem `usage.include`; `/models` OpenAI-compatible.
- **Mídia em resultados de tool (openai/openrouter)**: o Chat Completions só aceita texto em `role: tool` (verificado via OpenRouter: `openai/gpt-4o-mini` → 400 "Image URLs are only allowed for messages with role 'user'"; Claude e Gemini aceitavam, mas o formato precisa servir a todos). `hoistToolMedia` (attachments.ts, na cópia, antes de `expandAttachments`): cada msg `tool` com parts vira texto `[imagem: …]\n[imagem anexada na próxima mensagem]` (ou `[arquivo anexado …]`) e, logo após o bloco de mensagens `tool` consecutivas, entra uma `user` sintética **não persistida** `[...parts de mídia, {type:'text', text:'[arquivos retornados por read_file: a.png, b.pdf]'}]`. Derivada só do histórico → determinística (prefixo de cache estável); o histórico continua no formato neutro (Anthropic nativo usa tool_result com blocos). Verificado com gpt-4o-mini, claude-haiku-4.5 e gemini-2.5-flash-lite via OpenRouter (os três descrevem a imagem certo). O genérico `openai` usa o mesmo formato (o mais compatível; não testado em outro provider).
- **openrouter**: igual + `reasoning: {effort}`, `usage: {include: true}`, mantém `reasoning` no histórico, `/key` no teste, `input_modalities` no `/models`, PDF via file-parser em qualquer modelo.
- **anthropic** (API nativa): `POST {baseUrl}/messages` com `x-api-key`, `anthropic-version: 2023-06-01`, `content-type` (sem Bearer; `maskRequest` mascara qualquer header que contenha a key). O histórico persistido continua no formato OpenAI; a conversão é só na cópia enviada (`adapters/anthropic.ts`):
  - system → `system: [{type:'text', text}]` top-level; user parts: text → `text`, `image_url` data URL → `{type:'image', source:{type:'base64', media_type, data}}`, `file` PDF → `{type:'document', source:{type:'base64', media_type:'application/pdf', data}}`, áudio → texto `[áudio não suportado por este provider: nome]` (antes de expandir; o arquivo nem é lido);
  - assistant `tool_calls` → blocos `tool_use {id, name, input}` (`input` = JSON.parse dos argumentos; vazio → `{}`, inválido → `{raw}`); `reasoning` não é reenviado (sem assinatura); mensagens `tool` → `tool_result {tool_use_id, content}` dentro de um `user` (`content` string, ou blocos `text`/`image`/`document` quando o resultado tem parts — read_file de imagem/PDF; verificado com claude-haiku-4-5); mensagens consecutivas do mesmo role são mescladas (tools consecutivas + o user seguinte viram um único `user`); blocos de texto vazios saem (user vazio → `[mensagem vazia]`); se a 1ª mensagem for do assistant, entra um user `[início da conversa]`;
  - tools → `{name, description, input_schema}`; params: `max_tokens` (obrigatório: do chat, senão 32000 — 8192 p/ claude-3-5, 4096 p/ claude-3), `temperature`, `top_p`, `top_k`, `reasoning_effort` → `output_config: {effort}` (nível já ajustado ao modelo pelo `paramSupport`; a API só aceita low/medium/high/xhigh/max — verificado); penalties/seed ignorados; todos já filtrados pelo modelo ("Parâmetros por modelo"); thinking só via extraBody (reenviar blocos assinados não é feito); `extraBody` mesclado por último; `stream: true`; compactação com `toolChoiceNone` → `tool_choice: {type:'none'}`;
  - `cacheEnabled`: `cache_control` no último bloco do system, no último bloco da última mensagem e no da última mensagem com conteúdo de usuário (máx. 3 breakpoints);
  - stream SSE nativo: `message_start` (model, usage), `content_block_start` (text / tool_use {id,name} / thinking), `content_block_delta` (`text_delta`, `input_json_delta.partial_json`, `thinking_delta`), `message_delta` (stop_reason, output_tokens), `message_stop` (encerra), `error` (lança), `ping`. Usage: `promptTokens = input + cache_read + cache_creation`, `cachedTokens = cache_read`, `cacheWriteTokens = cache_creation`; `finishReason`: end_turn/stop_sequence → stop, tool_use → tool_calls, max_tokens → length. Erros HTTP `{type:'error', error:{type, message}}` → `readableError`;
  - `/models`: `GET {baseUrl}/models?limit=1000` (paginado por `after_id` enquanto `has_more`) → `name = display_name`, `contextLength = max_input_tokens`, `inputModalities = text + image (capabilities.image_input) + file (capabilities.pdf_input)`, `supportsTools = true`.
- Preview: `truncateBodyForPreview` também encurta `source.data` base64 dos blocos nativos.

### Parâmetros por modelo (`src/shared/modelParams.ts`)

Cada modelo aceita um subconjunto de `ChatParams`; o que ele não aceita **some do painel e não vai na request** — mas o valor salvo no chat **não é apagado** (volta a aparecer/ir se o chat trocar para um modelo que aceite).
- Fonte: **OpenRouter** → `ModelInfo.supportedParams` = `supported_parameters` do `/models` mapeado (`openRouterSupportedParams`: `max_completion_tokens` → `max_tokens`; `reasoning`/`reasoning_effort` → `reasoning_effort`); modelo fora da lista (ou sem a lista) = todos. **openai** genérico = todos. **Anthropic** nativa: o `/models` não informa amostragem → tabela `anthropicModelRules(id)` (`parseClaudeId`: família + versão do id):
  - `sampling: 'none'` (temperature/top_p/top_k → 400 "`X` is deprecated for this model"): Fable/Mythos, qualquer família ≥ 5, Opus ≥ 4.7. Doc: platform.claude.com/docs/en/build-with-claude/thinking ("Sampling parameters") e /api/messages ("Models released after Claude Opus 4.6…"); testado em haiku-5-5, sonnet-5-5, opus-5-5, fable-5-1, opus-5, sonnet-5, fable-5, opus-4-8, opus-4-7.
  - `'exclusive'`: os três aceitos, mas **temperature + top_p juntos → 400** ("cannot both be specified"): demais 4.x (testado: haiku-4-5, sonnet-4-6, opus-4-6, opus-4-5; release notes: Opus 4.1). Id não reconhecido também. A UI torna o par mutuamente exclusivo (ligar um desliga o outro, guardando o valor); se os dois estiverem ligados (ex.: chat vindo de outro modelo), a request manda só `temperature` e anota.
  - `'all'`: Claude 3.x (sem restrição documentada; não testado — aposentados).
  - `effort` (`reasoning_effort` visível): Fable/Mythos, ≥ 5, Opus ≥ 4.5, Sonnet ≥ 4.6 (doc /build-with-claude/effort `supportedModels`; haiku-4-5 testado → 400 "does not support the effort parameter").
  - penalties/seed: nunca (não existem na API nativa).
- **reasoning_effort — níveis por modelo** (`effortSpec` → `ParamRules.effort`; `null` = o modelo não aceita o param e ele some do painel). Ordem de fonte: **API → tabela conferida → conjunto comum**:
  - **OpenRouter**: o param só aparece se `supported_parameters` tiver `reasoning`/`reasoning_effort` (ex.: `openai/gpt-4o-mini`, `deepseek/deepseek-chat`, `openai/gpt-5.2-chat` → oculto). Níveis = objeto `reasoning` do `GET /models` (`openRouterReasoning`): `supported_efforts` (array → esses; `null` → todos os do gateway; ausente → não informado), `default_effort` (valor ao ligar o toggle), `mandatory` (sem `none`). Doc: openrouter.ai/docs/guides/best-practices/reasoning-tokens → "Discovering per-model reasoning options". O `/models/{autor}/{slug}/endpoints` só traz `supported_parameters` por provedor (sem níveis). Ex. (2026-10-16): gpt-5 `minimal…high`; gpt-5.1 `none,low,medium,high`; gpt-5.5 `none…xhigh`; gpt-5-pro `high`; claude-sonnet-4.6 `none,low,medium,high,max`; gemini-3.1-pro `low,medium,high`; o3/o4-mini, claude-opus-4.5, gemini-2.5-flash, deepseek-r1 → sem níveis.
  - **Anthropic nativa**: `capabilities.effort` do `GET /v1/models` (`anthropicCapsReasoning`: `supported` + `low/medium/high/xhigh/max.supported`) manda; sem `capabilities.effort` → tabela `anthropicModelRules(id).efforts` (doc /build-with-claude/effort → "Effort levels": low/medium/high em todos; `max` menos Opus 4.5; `xhigh` só ≥ 5 e Opus ≥ 4.7). Não existe `minimal`/`none`.
  - **openai** genérico: o `/models` da OpenAI não informa nada → tabela `openAIEffortRule(id)` (só ids conferidos contra os `supported_efforts` do OpenRouter + guia de reasoning da OpenAI): gpt-4*/3.5 sem raciocínio (oculto); série o e gpt-oss `low/medium/high`; gpt-5(-mini/-nano) `minimal…high`; gpt-5-pro `high`; gpt-5.1 `none…high`; gpt-5.2–5.5 `none…xhigh` (-pro: `medium/high/xhigh`). Se o endpoint devolver `supported_parameters`/`reasoning`, vale a API.
  - Sem informação → `low · medium · high`, marcado "não informado pela API" no (i); o valor salvo vai como está.
  - Valor salvo fora dos níveis **conhecidos** (ex.: `minimal` num série o; `xhigh` num claude-sonnet-4-6): a request manda o nível aceito mais alto ≤ pedido (sem contar `none`), senão o mais baixo acima; `none` não aceito → omitido. Nota no "Ver request" + aviso abaixo do seletor (`effortAdjust`). O valor salvo não muda.
  - Formato (`effortWire`): OpenRouter `reasoning: { effort }`; openai `reasoning_effort` na raiz; Anthropic `output_config: { effort }`. O (i) mostra formato, níveis e origem. Toggle desligado = nenhum desses campos.
  - **thinking** ligado no extraBody (`thinking.type` `enabled`/`adaptive`, só nos modelos que aceitam amostragem): `temperature` e `top_k` somem; `top_p` só ≥ 0.95 (abaixo → omitido com nota); sem par exclusivo. Testado em sonnet-4-6/haiku-4-5.
- `paramSupport({kind, model, info, extra, params})` → `supported` (painel), `exclusive`, `send` (o que vai), `omitted` + `notes` ("temperature omitido: não suportado por claude-sonnet-5-5 (…)."). Usado por `buildRequest` (→ `BuiltRequest.notes`, exibidas no "Ver request"), pela compactação (mesma request) e pelo juiz do Smart-Approve (`buildJudgeRequest`: o `temperature: 0` fixo é omitido onde não é aceito; antes um juiz claude-sonnet-5-5 nativo sempre falhava com 400). No main, `ModelInfo` vem do cache do `listModels` (`cachedModelInfo`, sem rede; vazio = desconhecido); no renderer, de `store.models`.

## Tools (`src/main/tools/`)

**Diretório raiz**: paths relativos resolvem contra `chat.config.cwd` (a raiz; `~` expande). Com `confineToRoot` (padrão), `list_dir`/`read_file`/`write_file`/`edit_file`/`search_files`/`find_files` rejeitam caminhos que, após `realpath` (seguindo symlinks — inclusive o ancestral existente mais profundo de um caminho que ainda não existe — e resolvendo `..`), fiquem fora da raiz: erro "acesso negado — … fica fora do diretório raiz" devolvido como `role: tool`. Sem confinação, absolutos são aceitos.

**Limites (higiene do contexto)** — `src/shared/limits.ts` (`LIMITS`), único configurável: `maxToolOutputChars` (padrão 30000; `runLocalTool` aplica como rede de segurança com corte início/fim). Cada card de tool mostra o tamanho aproximado do resultado enviado (caracteres ÷ 4 ≈ tokens).
- `read_file`: sem offset/limit lê no máx. 2000 linhas; linhas > 2000 chars cortadas com `[… linha cortada: N caracteres]`; teto de chars corta em linha inteira. Saída parcial começa com `[arquivo grande: 15.234 linhas, 820 KB — mostrando linhas 1–2.000. Use offset/limit para ler o resto, ou search_files para localizar trechos.]` (ou `[linhas X–Y de N (tamanho). Continue com offset=…]` com offset/limit); arquivo inteiro termina com `[fim do arquivo · N linhas]` (total de linhas sempre informado). > 5 MB sem offset/limit: não lê (tamanho + instruções); com offset/limit lê em streaming. Binário → recusa com tipo (PNG, PDF, ELF…) e tamanho — exceto imagem/PDF, abaixo.
- `read_file` de **imagem (png/jpg/jpeg/webp/gif, detectada pelos bytes) e PDF** (`src/main/tools/media.ts`): devolve o arquivo ao modelo **se o modelo da sessão lê o tipo** — `ToolContext.media = { providerKind, model() }` (runner: provider da sessão + `listModels` em cache, `find(id === session.model)`) e a mesma regra dos anexos (`modalitySupport`): `ok`/`parsed` (PDF no OpenRouter sem `file`: o file-parser extrai o texto) → devolve; `unsupported` → erro `Erro: Este modelo não lê imagens; read_file só pode devolver texto para ele — "a.png" é uma imagem PNG (140 KB). <dica>` (PDF: dica pdftotext / delegar); `unknown` (provider sem modalidades) → **imagem: devolve** (a maioria dos modelos OpenAI-compatible com visão aceita; se não aceitar, a API dá erro legível e o usuário apaga a mensagem) e **PDF: erro com dica** (parts `file` fora do OpenAI/OpenRouter são raros); sem contexto de mídia → recusa como binário. SVG é texto (XML). `offset/limit` são ignorados (aviso no resultado). Áudio: fora do escopo (continua recusado como binário).
  - **Resultado** (toolStatus `ok`): mensagem `tool` com `content: [{type:'text', text:'[imagem: shots/tela.png, 140 KB, 1280×720]'}, {type:'image_url', image_url:{url:'clearchat-attachment://<sha>.png'}, _attachment}]` (PDF: `[PDF: doc.pdf, 597 B, 1 página]` + part `file`). Bytes no store de anexos (`saveStoreFile`, content-addressed) — **nunca base64 no banco**; `expandAttachments` também expande msgs `tool`; GC enxerga a referência no `message_json`. `ToolResult.parts` / `ToolOutcome.parts` levam os parts até o `append`. Modo sem tools nativas: os parts entram na `user` sintética `<tool_result …>`.
  - **Limites** (`MEDIA_LIMITS`): imagem com lado maior > 2000 px ou > 3,75 MB (= 5 MB em base64) é **reduzida** (`setImageProcessor`; no app `nativeImageProcessor(nativeImage)` em `src/main/imageResize.ts`: redimensiona mantendo a proporção, PNG se couber, senão JPEG 85/70/55, encolhe 25% e repete) — o texto diz `reduzida de 4.000×3.000 (18 MB) para 2.000×1.333 (1,5 MB, JPEG)`; sem processador/falha → erro legível. Entrada > 50 MB não é decodificada. Fontes: Anthropic Vision (8000×8000 máx.; > 20 imagens na request → ≤ 2000 px cada, contando imagens em tool_result; 10 MB base64 na API direta, **5 MB base64 no Bedrock/Vertex** — rota comum do OpenRouter; lado nativo 1568 px / 2576 px nos Claude 4.7+), OpenAI Images and vision (png/jpeg/webp/gif não animado; high detail encaixa em 2048). PDF: ≤ 10 MB e ≤ 100 páginas (Anthropic PDF support: request ≤ 32 MB, 100 páginas com janela < 1M; contagem heurística `/Type /Page`, PDFs com object streams podem não ser contados) → erro legível com dica.
  - **Texto/derivados**: `contentText` (copiar, ToolCard, cartões órfãos/sintéticos), `read_history` (texto + `[anexos: a.png]`; omitido → `… caracteres + 1 anexo(s)`), Smart-Approve (contexto), compactação `trimmed`/`tail` (mídia → `[imagem: nome]`), preview (`truncateBodyForPreview` encurta também `source.data` dentro de `tool_result.content`), `withText` (edição mantém os parts de mídia, texto primeiro). **ToolCard**: miniatura clicável (lightbox) / chip de PDF abaixo do cabeçalho (`ToolResultMedia`); o selo de tamanho mostra `~N tok + mídia` (tokens de imagem/PDF vêm no usage real da resposta, que o medidor de contexto já usa).
  - **Verificado de verdade** (read_file → buildRequest → streamChat do app): Anthropic nativo claude-haiku-4-5 descreve a imagem (fundo vermelho, "ZEBRA 42") e lê o PDF ("PAPAYA") dentro do tool_result; OpenRouter (fallback user) gpt-4o-mini, claude-haiku-4.5 e gemini-2.5-flash-lite descrevem a imagem. PDF via OpenRouter **não verificado** (402: saldo < US$ 0,50 exigido para arquivos).
- `shell`: mantém início (40%) e fim (60%) com `[… N chars / M linhas omitidos …]` + dica de redirecionar para arquivo e usar grep/head/tail.
- `browse_url`: texto paginado (12.000 chars/página) com `offset`; cabeçalho `[caracteres X–Y de Z — continue com offset=…]`; texto extraído em cache por sessão+URL por 5 min (paginação não recarrega); links só na 1ª página (máx. 40).
- `list_models`: padrão 50 modelos (máx. 200, `modelsDefaultResults`/`modelsMaxResults`), corta antes do teto de saída com dica para refinar.
- `web_search`: máx. 8 resultados (buscadores com API: opção "Resultados" 1–10), trecho ≤ 300 chars (com a data `AAAA-MM-DD — ` na frente quando o buscador informa). **UM buscador por pesquisa** (`tools/webSearch.ts` puro, backends injetados; `web.ts` liga os reais): o **primeiro habilitado** na ordem de Configurações → **Pesquisa na web**; se ele **falhar**, a MESMA pesquisa passa para o próximo habilitado — resultados de buscadores diferentes **nunca** são misturados. Falha (`EngineOutcome.kind = 'fail'`, `FailCategory`): `no-key` (exige chave e não tem — sem rede), `auth` (HTTP 401/403 e o 422 `SUBSCRIPTION_TOKEN_INVALID` do Brave), `quota` (402/429/432/433), `blocked` (captcha/anti-robô), `network` (erro de rede/timeout 20 s), `http` (demais ≥ 400), `empty` (corpo vazio/JSON em formato inesperado; no DDG, 0 resultados sem a marca de "sem resultados"). **"Sem resultados" legítimo NÃO faz fallback** (JSON válido com `results: []`, página "no results" do DDG, Brave (site) sem resultados e sem bloqueio) → `Nenhum resultado de <buscador> para "x".` 1ª linha: `Resultados de <buscador> para "x":` ou, se alguém falhou antes, `Resultados de Tavily para "x" (após falha em Exa: limite de uso/cota atingido (HTTP 429) — <detalhe curto do corpo>; DuckDuckGo: verificação anti-robô (captcha)):`. Tavily com `answer` → linha `Resposta resumida: …` (≤ 600 chars) antes da lista. Todos falhando → `Erro: a pesquisa falhou nos N buscadores habilitados — Exa: …; Tavily: …. ### Shell do usuário (`src/main/tools/shellEnv.ts`, `src/shared/shellInfo.ts`)

- **Escolha** (`pickShell` / `resolveShell()`): `$SHELL` se o basename for `zsh` ou `bash` e o arquivo existir; senão bash (`/bin/bash`, `/usr/bin/bash`, … ou `bash` do PATH) — fish/sh/outros → bash. Versão via `<shell> --version` uma vez (cacheada). `ShellKind` já reserva `'pwsh'` (pendência: Windows/PowerShell não implementado; o app empacota só Linux e roda em macOS no dev).
- **Ambiente resolvido uma vez** (como o VS Code): `initShell()` no start do app (index.ts) detecta o shell e dispara, em segundo plano, `<shell> -ilc "printf MARCADOR; env -0; printf MARCADOR"` (detached, stdin ignorado, timeout 10 s, sem `ELECTRON_RUN_AS_NODE`). O env é extraído entre os marcadores (lixo do .zshrc antes/depois é ignorado; `SHLVL`, `PWD`, `OLDPWD`, `_` etc. descartados). Cada comando roda com env = `{...process.env, ...envResolvido, CLEAR_START_DIR, CLEAR_ROOT_DIR}` e **`<shell> -c`** (sem `-l`: no macOS o `/etc/zprofile` (path_helper) reordenaria o PATH e esconderia o nvm). Falha/timeout → `process.env` + `<shell> -lc` (logado). A 1ª chamada espera a resolução (~0,8 s com zsh -i); as seguintes, não. `CLEARCHAT_SKIP_SHELL_ENV=1` desliga.
- **Descrição da tool `shell`** = `shellDescriptionPrefix(info)` + texto fixo: "Executa um comando no shell do usuário: zsh 5.9 (macOS) — use sintaxe zsh: arrays começam em 1; glob sem correspondência é erro (nomatch…); $var não sofre word splitting…". bash < 4 (o 3.2 do macOS): "bash 3.2 antigo: sem arrays associativos, mapfile/readarray, ${var,,}…". bash 5: sem dicas. Sem info: "(zsh ou bash)". Determinística por máquina (só nome, versão e SO — estável para cache de prompt). O main injeta com `setToolShellInfo` (shared); `toolDefinitionFor('shell')` / `currentToolDefinition` usam. O renderer recebe a mesma info em `app.capabilities().shell` e injeta igual (o (i) das tools e o texto de tools no prompt mostram o mesmo texto da request).
- **Bloco `<environment>`**: `shellLabel()` (bash.ts/shellEnv.ts; ex. "zsh 5.9", fallback "bash") — a aplicar em `defaultEnvInfo()` de request.ts (`shell: shellLabel()`).
- Pendência: config por chat para forçar o shell.

### Migração bash → shell (`src/main/migrateTools.ts`, `src/shared/toolRename.ts`)

## Smart-Approve (`src/shared/smartApprove.ts`, `src/main/agent/smartApprove.ts`, runner)

Um modelo "juiz" (qualquer par provedor + modelo) decide as chamadas dos itens em modo `smart` antes de perguntar ao usuário. Config por chat em `ChatConfig.smartApprove` (também nas personas, via `PRESET_FIELDS`). **Não há liga/desliga** (0.5): o juiz age exatamente nos itens cujo modo efetivo é `smart`, desde que haja modelo (`smartApproveActive` = `judgeConfigured` = provedor + modelo).
- **Quando o juiz é chamado**: itens (ver "Aprovações" — inclui `write_file`, `edit_file`, `send_to_chat`, `delegate_task`) cujo modo efetivo é `smart`. `argsSummary` mostra o comando + cwd de `process_start`. Modo `smart` sem modelo → pergunta ao usuário (fail-closed; `ApprovalRequest.smartMissing`, o card avisa "Configure o modelo do Smart-Approve"). `normalizeSmartApprove` descarta as chaves legadas `enabled`/`tools`.
- **Ordem** (modo smart): juiz → usuário. Resultados do juiz: `approve` → roda; `reject` → não roda, resultado de tool `Rejeitado pelo Smart-Approve (<modelo>): <motivo>` (toolStatus `denied`) para o agente se adaptar; `ask` → card de aprovação normal com o motivo do juiz. **Fail-closed**: erro HTTP/rede, tempo esgotado (`timeoutS`), resposta vazia, sem rótulo ou com mais de um rótulo distinto → card de aprovação (`fallback` `error`/`timeout`/`ambiguous`). Nunca libera por falha. Parar/⚡ durante a avaliação cancela a chamada.
- **Chamada ao juiz** (fora do histórico, nunca persistida como mensagem; o agente não a vê): `POST {baseUrl}/chat/completions` do provedor do juiz, headers = `buildHeaders(provedor, assinatura do chat)`, body `{ model, messages: [system, user], temperature: 0, max_tokens: 300, stream: true, stream_options, usage? (OpenRouter) }` — stream acumulado (aceita JSON se o provedor ignorar `stream`). System = `prompt ?? DEFAULT_SMART_APPROVE_PROMPT` (inglês de propósito: formato estrito mais confiável; o motivo vem no idioma do usuário); user = `template ?? DEFAULT_SMART_APPROVE_TEMPLATE`. Placeholders (system e template, uma passada, desconhecidos ficam): `{{tool}}`, `{{args}}` (JSON formatado), `{{cwd}}`, `{{confine}}` / `{{sandbox}}` (yes/no), `{{last_user_message}}` (última `role: user` da sessão — na subsessão, a tarefa —, sem fronteiras/callbacks/`<tool_result>`, ≤ 2.000 chars), `{{recent_context}}` (últimas `contextMessages` mensagens ativas: `[user] …`, `[assistant] …` + `→ tool(args ≤ 300)`, `[tool nome] resultado ≤ 300`, cada texto ≤ 600; 0 = `(omitted)`), `{{labels}}` (`A | R | P`), `{{approve}}`, `{{reject}}`, `{{ask}}`.
- **Parse** (`parseJudgeOutput`): ignora `<think>…</think>`, `*`, crases, `~~`, `#`/`>`/marcadores; a 1ª linha não vazia precisa **começar** com um rótulo (sem caixa; tolera `Decision:`/`Veredito —`/aspas/colchetes; fronteira: nem letra/dígito/`_`/`-` colados — `ASK` ≠ `ASK-USER`); outro rótulo distinto na mesma linha (sem caixa) ou nas linhas seguintes (caixa exata) → ambíguo. Resto = motivo (uma linha, ≤ 500).
- **Registro**: `SmartApproveRecord` na meta da mensagem tool (`meta.smartApprove`) e na `ApprovalRequest` (decisão `ask`). Inclui a request mascarada e a resposta crua (para o (i)), usage/custo e duração. Subagentes usam a mesma config com o próprio histórico.
- **"Executar mesmo assim"** (`agent.smartOverride(messageId)`): a rejeição continua sendo o resultado daquela chamada (o histórico não é reescrito, o pareamento tool_call/tool não muda). Ao clicar, (1) o app registra uma **liberação de uma vez só** em memória para a mesma sessão + mesma tool + mesmos argumentos (`argsKey`: JSON com chaves ordenadas; expira em 15 min ou ao reiniciar) e (2) entrega à sessão a mensagem do usuário ``Pode executar <tool> `<args resumidos>`; eu aprovo.`` (fila se estiver rodando; senão inicia um turno). Quando o agente repete a chamada idêntica, ela roda sem juiz nem card (`meta.smartOverride`); qualquer variação passa pelo juiz de novo (que agora vê a autorização explícita no contexto). A rejeição fica marcada `overridden` (o botão vira "Liberado · …").
- **UI**: card da tool com status "Smart-Approve avaliando" (evento `tool-running` com `judging`), linha compacta "Aprovado pelo Smart-Approve · <Provedor · modelo> · custo · duração" (verde) / "Rejeitado…" (vermelho, com "Executar mesmo assim") / "Smart-Approve pediu sua decisão" ou "não decidiu (tempo esgotado | erro na chamada | resposta ambígua)" (âmbar, dentro do card de aprovação), motivo abaixo e (i) com a request exata + resposta. Rodapé da resposta do assistente: "juiz $x" (tooltip: chamadas, tokens, custo — fora do histórico).
- **Aba Tools → Smart-Approve**: seletor de modelo (placeholder "Nenhum" + × "Remover modelo (itens em Smart-Approve passam a perguntar)"), linha `smart-approve-hint`: com modelo "Decide: <itens>." / "Nenhum item está no modo Smart-Approve"; sem modelo "Escolha um modelo para poder usar o modo Smart-Approve nos itens acima." ou, com itens em smart, aviso âmbar "Escolha um modelo: sem ele, <itens> pedem sua confirmação."; rótulos (validados: não vazios, distintos, uma linha — inválido não salva), mensagens de contexto, tempo máximo, prompt + template com "Restaurar padrão" e cola de placeholders, (i) com a request exata para a chamada de exemplo e "Testar" (`agent.smartApproveTest`: tool + args editáveis, contexto de exemplo, mostra a decisão).
- **Header**: ver "Aprovações → UI".

## Aprovações (`src/shared/approvalPolicy.ts`, `src/shared/shellParse.ts`, `src/main/approvalSettings.ts`, runner)

Gate de toda chamada de tool. **Itens** (`APPROVAL_ITEMS`, um por tool — `ITEM_TOOL`/`TOOL_ITEM`/`APPROVAL_TOOLS`; grupos da UI em `APPROVAL_ITEM_GROUPS`): *Terminal e web* — **Comandos** (`shell`), **Processos** (`process_start`), **Páginas** (`browse_url`), **Busca web** (`web_search`); *Arquivos e agentes* — **Escrever arquivo** (`write_file`), **Editar arquivo** (`edit_file`), **Enviar para chat** (`send_to_chat`), **Delegar a subagente** (`delegate_task`); *Memória* — **Gravar memória** (`memory_write`), **Reescrever memória** (`memory_rewrite`), **Apagar memória** (`memory_delete`) — ids de item iguais aos nomes das tools, padrão global `always` e terceira opção "Perguntar" (como os de arquivo). `process_stop` **nunca** pede aprovação (só alcança processos do próprio chat). As demais tools (leitura, histórico, `list_models`, controle de subagentes, `ask_user`) rodam direto.

**Modos** (por item): `always` (Sempre permitir — roda sem perguntar; a blacklist NÃO vale) · `smart` (o juiz do Smart-Approve decide, com a config do chat; sem modelo → pergunta, fail-closed) · `lists` (Whitelist/Blacklist em Comandos/Processos/Páginas — `isListItem`; nos demais itens = **Perguntar** sim/não, sem listas — decisão: buscas não têm um "alvo" útil para listar e a consulta pode vazar contexto; para arquivos/chats/subagentes "Perguntar" é a terceira opção natural). `modeLabel`/`modeHint` dão o rótulo e o tooltip por item.
- **Escopo**: modo **global** por item (settings `approvalModes`, Configurações → Aprovações) + **ajuste por chat** (`ChatConfig.approvalModes[item]`; aba Tools e personas via `PRESET_FIELDS`). Modo efetivo = chat ?? global ?? `DEFAULT_APPROVAL_MODES` (`effectiveMode`). Subagentes usam o modo efetivo do chat. As **listas são sempre globais** (settings `approvalLists` = `{ commands, processes, pages }` × `{ allow, deny }`), nunca por chat.
- **Padrão global** (`DEFAULT_APPROVAL_MODES`): `lists` em Comandos/Processos/Páginas/Busca (com listas vazias = tudo pergunta, como nas versões anteriores; o usuário vai liberando com "+ whitelist") e `always` em Escrever/Editar arquivo, Enviar para chat e Delegar (rodavam sem perguntar antes de virarem itens) — nada muda de comportamento numa atualização. Um global salvo antes dos itens novos existirem é completado com esses padrões (`normalizeApprovalModes`).
- **Rota** (`approvalRoute(cfg, globalModes, tool)` → `run | judge | user{smartMissing?} | lists`), no runner (`executeTool`): não-item → run; `always` → run; `smart` → judge (sem modelo → user + smartMissing); `lists` → lists (itens de lista) ou user. `takeOverride` ("Executar mesmo assim") vale para qualquer rota ≠ run.
- **★ e herança** (`withChatMode(overrides, item, escolha, global)`): na aba Tools/personas cada item mostra só as 3 opções; a igual ao modo global tem ★ ("Padrão global"). Sem override o chat segue o global (a opção ★ aparece marcada; acompanha mudanças do global). Escolher a opção ★ grava **sem override**; escolher outra grava o override. Um override igual ao global (ex.: o global mudou depois) aparece marcado na opção ★ e clicá-la remove o override.

### Modo `lists` — Comandos e Processos
1. **Parser conservador próprio** (`analyzeShell`, sem dependências; nunca executa/expande nada) desmonta o comando em **sub-comandos**: `|`, `|&`, `&&`, `||`, `;`, `&`, quebras de linha, `( … )`, `{ …; }`, `if/while/for` (palavras reservadas puladas; cabeçalho `for x in …` não é comando). Aspas simples/duplas, `$'…'`, escapes e continuação de linha respeitados (`;` em aspas não separa; `\|` é literal); `#` só no início de palavra é comentário. Cada sub-comando = tokens sem aspas (o mesmo tokenizer dos padrões).
2. **Construtos que escondem comandos** → o conteúdo é analisado: `$(…)` e crases (também dentro de aspas duplas; em aspas simples não) viram sub-comandos extras (nota "dentro de $(…)"); `bash|sh|zsh|dash|ksh -c "…"` analisa a string; prefixos `env`, `nice`, `time`, `nohup`, `command`, `exec`, `builtin`, `noglob`, `timeout`, `stdbuf` e atribuições `VAR=v` são removidos (avalia o comando). **`sudo`/`doas`** (decisão): viram DOIS sub-comandos — `sudo …` inteiro (precisa casar sozinho com a lista, ex. `sudo apt *`) **e** o comando interno; assim "liberar `apt update`" não libera `sudo apt update`, e a blacklist do interno também pega sob sudo.
   **Sempre perguntar** (`unsafe` — nunca auto-aprovado mesmo com whitelist; a blacklist continua valendo): `eval`, `source`/`.`, `xargs`, `find -exec/-execdir/-ok/-okdir`, `fd --exec`, `<(…)`/`>(…)` (o interno também é analisado), heredoc alimentando algo que não seja consumidor de dados conhecido (`cat`, `grep`, `jq`…) ou com `$(…)` no corpo sem aspas no delimitador, `alias`, `function`/`f() …`, `trap`, `case`, `select`, `coproc`, `watch`, `parallel`, `hash -p`, `enable`, nome de comando vindo de expansão/glob (`$CMD x`, `./r*`), `=cmd`, glob qualifiers/extglob `*(…)`, **expansão de chaves** `{a,b}`/`{1..3}` (`{rm,-rf,x}` = `rm -rf x`), `$(( $(…) ))`, `sh`/`bash` lendo do stdin (`curl … | sh`, `bash -s`), `env -S`, atribuição/`export` de variáveis que mudam qual programa roda ou injetam código (`PATH`, `LD_*`, `DYLD_*`, `BASH_ENV`, `IFS`, `NODE_OPTIONS`, `GIT_*SSH*`…), **redirecionamento de saída para arquivo** (`>`, `>>`, `>|`, `&>`, `2>` … para algo ≠ `/dev/null`, `/dev/stdout|stderr|tty`, `&N`; o destino aparece no motivo) e qualquer erro de sintaxe (aspas/parênteses sem par → um item só com o texto inteiro).
3. Para cada sub-comando: casa com a **blacklist** → o comando INTEIRO é bloqueado sem perguntar: resultado `Bloqueado pela blacklist (comandos): "<entrada>" casou com "<sub-comando>"` (processos: `(processos)`), toolStatus `denied`. A blacklist precede a whitelist. Casa com a **whitelist** (e não é `unsafe`) → ok. Nenhum → precisa de decisão.
4. Algum pendente → UM card (`ApprovalRequest.check`) com TODOS os sub-comandos: liberados marcados (✓ whitelist "<entrada>"), pendentes com **[Sim] [Sim + whitelist] [Não] [Não + blacklist]** ("Sim + whitelist" desabilitado em `unsafe`). Executa só quando todos forem Sim; o primeiro Não já responde (nada roda): resultado `O usuário negou: <sub-comando>` (denied). "Sim para todos" quando há 2+ pendentes. Parar/⚡/fila: igual aos cards atuais (abort → cancelado).
5. **"+ whitelist/blacklist"**: campo editável pré-preenchido com `suggestCommandPattern` — `programa subcomando *` quando o programa tem subcomandos conhecidos (git, npm, docker, cargo, kubectl, gh…) e o 1º argumento logo após o programa é alfabético (`git push origin main` → `git push *`); senão `programa *` (`ls -la` → `ls *`); `sudo x …` → `sudo <sugestão de x>`. Confirmar valida (`validateListEntry`), salva na lista global (`addListEntries`: sem duplicar; a entrada sai da lista oposta do mesmo item) e aplica a decisão. Aviso suave quando o padrão é só `programa *` ("`git *` libera QUALQUER uso de git (ex.: git push --force…)").
   **Semântica do padrão** (`matchCommandPattern`): casamento por TOKENS após normalização (mesmo tokenizer: aspas removidas, espaços colapsados); `*` como token sozinho casa **zero ou mais** tokens; `*` dentro de um token é glob dentro do token (`npm run test:*` casa `test:unit`, não cruza tokens); `\*`/`'*'` = asterisco literal; sem `*` = **exato**. Ex.: `git push *` casa `git push` e `git push -f origin x`, não `git pull`; `rm -rf ./dist` casa só isso. Na **blacklist**, um padrão cujo programa não tem `/` casa também o basename (`rm *` bloqueia `/bin/rm -rf x`); na whitelist não (`ls *` não libera `./ls`). `*` sozinho é recusado.
6. **Processos** (`process_start`): mesma análise, com listas próprias.
- Mudança nas listas com cards abertos (outro card salvou "+ whitelist", Configurações): o runner reavalia os cards cujo veredito mudou (`onApprovalListsChanged` → resolve `reeval` → nova avaliação; pode virar bloqueio, execução direta ou um card atualizado).

### Modo `lists` — Páginas (`browse_url`)
Entrada = **domínio** (`github.com` — só esse host; `*.github.com` — o domínio e qualquer subdomínio; opcional `:porta`; vale para http e https; `*.com` recusado) **ou prefixo de URL** (`https://github.com/ezenere/` — mesmo esquema/host/porta e caminho com esse prefixo em fronteira de segmento: `/ezenere` casa `/ezenere` e `/ezenere/x`, não `/ezenere2`; com `?`/`#` compara a URL inteira por prefixo). Normalização via WHATWG `URL` (esquema/host minúsculos, sem porta padrão, IDN → punycode; sem esquema → https, como o browse_url). Blacklist precede. Mesmo card de 4 botões (um item; "+ lista" pré-preenche com o host). URL inválida/não http(s) → pergunta.

Card da tool: "Liberado pela whitelist: …" (verde), "Bloqueado pela blacklist: <entrada> casou com <sub-comando>" (vermelho), "Você negou …". Modo `always`: sem linha (o selo do header mostra).

No chat: aviso vermelho compacto acima do composer — "Subagente “X” falhou: <erro curto> · Abrir subsessão · ×" — quando o card do delegate não está na tela; some ao **dispensar** (×), ao abrir a subsessão, quando o card do delegate fica visível (vira "visto") ou quando o subagente volta a rodar/conclui. O card do delegate mostra a linha vermelha "Subagente falhou: …" enquanto a subsessão estiver em `error`. Falhas não sobrevivem a reiniciar o app (decisão: dado mínimo, sem schema novo).
- E2E: `e2e/approval-queue.spec.ts` (`npm run test:e2e:queue`); unit: `e2e/approvalQueue.test.ts`.

### Limitações conhecidas do parser
- **Avaliação indireta** (revisão de segurança): o VALOR de uma variável pode virar código em `$((x))`, `$[x]`, subscritos `${a[$x]}`, `let`, `declare/typeset -i`, `integer`/`float`, `[[ $x -eq … ]]` (bash: `x='a[$(cmd)]'` executa `cmd`) e nas flags do zsh `${(e)x}`/`${(P)x}`/`${~x}`/`${!x}`. Todos esses **sempre perguntam**; só aritmética com literais (`$((1+2))`, `[[ 2 -gt 1 ]]`) e expansões simples (`$x`, `${x:-y}`, `${#x}`) podem ser liberadas.
- **Padrões amplos (`programa *`)**: o parser não conhece a semântica das opções de cada programa. Vários executam comandos arbitrários por opção (`git -c core.pager=…`, `git diff --ext-diff`, `sed '1e …'`, `awk 'BEGIN{system(…)}'`, `tar --to-command`, `rg --pre`, `ssh host cmd`, `find -delete`). A whitelist casa só o texto, então `git *`/`sed *`/`awk *` liberam isso. O editor avisa; prefira subcomandos específicos (`git status *`). Opções antes do subcomando (`git -c … status`) não casam `git status *` (pergunta).
Não entende `case … esac`, `select`, arrays `a=(…)`, `[[ … =~ … ]]` com parênteses na regex, here-strings com substituições aninhadas complexas e aliases já definidos no shell do usuário (um alias `ls='rm -rf'` no `.zshrc` não é visível — é um risco aceito; o padrão casa o texto, não o binário). Prefixos desconhecidos (ex.: `chronic x`, `caffeinate x`, `npx x`) são tratados como o próprio programa (o usuário decide o padrão). Opções desconhecidas de `sudo`/`env`/`nice`/`timeout` → pergunta. Variáveis em argumentos (`rm -rf $DIR`) ficam literais (`$DIR`) — o padrão `rm -rf $DIR` só casa o texto literal.

## Contexto e compactação (`src/shared/context.ts`, `src/main/agent/compaction.ts`, runner)

- **Janela** (`resolveContextWindow`): principal = `contextWindow` (override) → `ModelInfo.contextLength` (`/models`, `context_length`); subsessão = janela do próprio modelo → override.
- **Uso** (`contextUsage`): `promptTokens + completionTokens` da última resposta do assistente após a fronteira mais recente; sem resposta desde a compactação → `meta.contextEstimate` da fronteira (estimativa).
- **Limite**: `compactThreshold` (0.9). ≥ limite → banner "Contexto em 92% — Compactar conversa". `autoCompact` (principal) / sempre (subsessões): compacta sozinho no limite de passo; também ao receber erro de contexto excedido (`isContextLengthError`: "maximum context length", "context_length_exceeded", "prompt is too long", …; ignora rate-limit/TPM), uma vez por chamada bem-sucedida.
- **Compactação** (`agent.compact` ou automática): roda no limite de passo (ociosa: loop só de compactação, status `running`; rodando: agendada, evento `compaction{state:'scheduled'}`; agendada no último passo → roda e encerra o turno, salvo fila/⚡). `repairTail` antes (nunca no meio de um par tool_calls ↔ tool). Request = **a request normal** (mesmas tools, system, params, histórico ativo e breakpoints → prefixo do cache) + último `{role:'user', content: compactPrompt}`; stream visível (`compaction{state:'running', text}`). Se a request estourar o contexto: tenta `trimmed` (resultados de tool/mensagens longas encurtados) e depois `tail` (só as mais recentes que cabem); resposta vazia → repete com `tool_choice:'none'`. Nem a request nem a resposta são persistidas: só a **fronteira** `role: user`, content = `compactionMessageText(resumo, faixa?)` = `<conversation_summary>\n…\n</conversation_summary>\n\n` + nota — decidida **na hora da compactação** (o texto é persistido): com `read_history` disponível para a sessão, `compactionNoteWithHistory(X, Y)` = "O histórico anterior desta conversa (mensagens #X–#Y) foi compactado … As mensagens originais continuam salvas: … consulte-as com a ferramenta read_history …" (X = primeira mensagem salva, Y = última resumida); sem ela, `COMPACTION_NOTE` ("… as mensagens originais não estão mais disponíveis …"), meta `{ kind:'compaction', synthetic:true, summaryOf, compactedCount, usageBefore, contextEstimate, compactUsage, model, durationMs }`. `buildRequest` envia só da fronteira mais recente em diante (system continua primeiro; tool órfão logo após a fronteira é descartado por `sanitizeHistory`). Parar/⚡ durante a compactação cancela sem salvar nada. Apagar a fronteira desfaz a compactação. `{retry:true}` ("Compactar e tentar de novo") roda o agente depois.

## Mensagens entre chats (`send_to_chat`, `src/shared/interChat.ts`, runner)

- Entrega no **chat de destino** (sessão principal) exatamente como se o usuário digitasse: ociosa → inicia um turno; rodando → fila (`QueuedMessage.meta`), injetada no próximo limite de passo. As aprovações do destino continuam valendo lá.
- Conteúdo persistido = `interChatHeader(título, id, { waitForReply, canReply })` + `\n` + mensagem: `[Mensagem do chat "Título" (id …)]`, com o sufixo `— o remetente aguarda: sua resposta final neste turno será devolvida a ele automaticamente` (wait) ou `— se precisar responder, use send_to_chat com chat_id "…"` (se o destino tiver a tool). Meta `{ kind:'inter-chat', fromChatId, fromSessionId, fromChatTitle, interChatHops }`. O título automático do destino usa só o corpo.
- `wait_for_reply`: aguarda o fim do turno do destino que processa a mensagem e devolve `Resposta do chat "T" (id …):\n\n<texto final>`; tempo esgotado → `[O chat "T" … ainda está rodando após Ns; a resposta ficará no chat …]`; erro do destino → erro; turno interrompido / mensagem presa na fila → aviso. Sem wait: "entregue … iniciou um turno" / "enfileirada …". Parar/⚡ do remetente cancela só a espera (a mensagem já entregue fica).
- **Segurança**: recusa o próprio chat; **saltos** — `currentInterChatHops(histórico da principal do remetente)` = saltos da última mensagem do usuário (não sintética) se ela for inter-chat, senão 0; a nova mensagem leva +1 e acima de 3 (`LIMITS.interChatMaxHops`) é recusada; **ciclo de espera** — grafo em memória de esperas (chat que espera → chat aguardado); `wouldCreateWaitCycle` recusa A aguardar B se já houver caminho B → … → A (em vez de travar). `chat_id` aceita prefixo único (≥ 4).
- UI: no destino, bolha distinta "De: <título>" (link abre o chat de origem; "(chat apagado)" se não existir; saltos > 1 indicados) com (i) mostrando o objeto exato (com o cabeçalho). No remetente, o card mostra o chat de destino, "Abrir chat" e a resposta (quando aguardada). A sidebar reflete o destino ocupado via `session-updated` (aplicado para qualquer chat, aberto ou não) e `chat-updated` (ordem/“atualizado”).

## Histórico (`read_history`, `src/main/tools/history.ts`)

Lê as mensagens **persistidas** da sessão chamadora (subagentes leem a própria) — ou, com `chat_id` / `scope: "all"`, de outros chats (abaixo) —, inclusive as anteriores às fronteiras de compactação; exclui erros só de exibição. Cabeçalho: `[histórico desta sessão: N mensagens (#a–#b); fronteiras de compactação: #12 (resume #1–#11) — as mensagens antes de #12 não estão mais no seu contexto]`.
- **Faixa** (sem `query`): `#seq papel: conteúdo` (`user`, `user (app)`, `user [de outro chat]`, `user [fronteira de compactação · resume #x–#y]`, `assistant` + `→ chamou tool(args…)`, `tool (nome[, status])`); resultados de tool só com `include_tool_results` (senão `[resultado omitido · N caracteres …]`); cada mensagem ≤ 2.000 chars (início 70% + fim 30% com `[… N caracteres omitidos — leia inteira com from_seq=S to_seq=S]`), exceto ao ler uma só (inteira, até o teto). Padrão 40 mensagens (máx. 200): sem from/to = início do histórico; só `to_seq` = as últimas até ele. Respeita `maxToolOutputChars`; rodapé `[mostrando #a–#b … continue com from_seq=…]`.
- **Busca** (`query`): sem caixa, em texto, argumentos e resultados de tools (ignora as chamadas/resultados do próprio read_history); sem a frase exata, mensagens com todos os termos. Padrão 20 resultados (máx. 100), até 2 trechos de ~220 chars por mensagem: `#seq papel: …trecho…`. `from_seq`/`to_seq` filtram.
- Sem `chat_id`/`scope` a busca na sessão do chamador continua **substring** em memória (ordem de seq; acha qualquer pedaço, ex. `8123`, `config.json`) — o FTS é usado só para outros chats.

### Outros chats (só leitura; `src/main/historyStore.ts`, `src/main/searchIndex.ts`)

- **`scope: "all"` + `query`**: busca em todos os chats **exceto o do chamador** (o chat inteiro, inclusive as subsessões dele; subagentes também excluem o próprio chat). Ranking bm25 (FTS5), resultados agrupados por chat na ordem do melhor resultado: `## "Título" · chat_id <id> · atualizado AAAA-MM-DD · N mensagens` + até 3 trechos (`LIMITS.historyAllPerChat`) `#seq papel[ subagente "T" · session_id xxxxxxxx]: …trecho…`; padrão 5 chats (`limit`, máx. 20); sobrando chats → "Há mais N chat(s)". Cabeçalho `[busca em N chats (exceto este) por "q": M mensagens com todos os termos em K chats; mostrando …]`; sem resultado com todos os termos → refaz com qualquer termo ("com algum dos termos"); chats cujo título tem todos os termos e não apareceram → `[chats com título parecido: …]`. Teto `maxOutputOf(ctx)`. Exige `query`; `chat_id` + `scope` = erro.
- **`chat_id`** (id ou prefixo único ≥ 4, como send_to_chat; ambíguo/não encontrado = erro): sem `query` = **faixa** da sessão principal daquele chat (mesmo formato da faixa local; cabeçalho `[histórico do chat "T" (id …, sessão principal; N subagentes): …]`, sem a nota "não estão mais no seu contexto") — é como "abrir" um resultado. Com `query` = busca FTS no chat inteiro (principal + subagentes; com `session_id`/`from_seq`/`to_seq`, só naquela sessão). `session_id` (id ou prefixo ≥ 4 de uma subsessão do chat) troca a sessão lida; sem `chat_id` = erro. Pode ser o próprio chat (útil para ler outra sessão dele).
- **Índice FTS5**: `message_search` mapeia `docid` estável ↔ `messages.id` (VACUUM não renumera INTEGER PRIMARY KEY); `messages_fts` é **contentless** (`content=''`, `contentless_delete=1`, SQLite ≥ 3.43 — o better-sqlite3 13 traz 3.53 com `SQLITE_ENABLE_FTS5` em todos os prebuilds): só o índice invertido; os trechos são recortados em JS do texto pesquisável da mensagem (`matchSnippet`: ao redor da primeira ocorrência, início de palavra, sem acento/caixa). Colunas: `body` (texto de user/assistant + nomes de anexos) e `tool` (chamadas `nome(args)` e resultados de tools), bm25 pesos 3:1. **Texto pesquisável** (`searchableText`): nunca bytes de anexos; sequências ≥ 200 chars de base64/hex removidas; ≤ 60k chars por coluna; fora: erros só de exibição, chamadas de read_history e as saídas dele.
- **Consulta** (`ftsQuery`): a entrada do agente é tokenizada em JS (letras/números Unicode); cada pedaço separado por espaço vira frase entre aspas (aspas duplicadas), com prefixo `*` se o último token tem ≥ 3 chars; termos unidos por AND (fallback OR). Operadores do FTS (`NEAR(`, `AND`, `col:`, `^`, `*` sozinho, aspas) perdem o sentido; nada pesquisável → aviso, sem erro.
- **Manutenção**: `ensureSearchIndex(conn)` em `migrate()` (db.ts): cria tabelas + trigger (idempotente); popula quando a flag `settings['migration.searchIndex']` ≠ `SEARCH_INDEX_VERSION` (suba-a ao mudar as regras → reindexa tudo) ou a tabela não existia; em lotes de 500 numa transação. Inserção/edição pelo repo (`indexMessage` em `append`, `insertAt`, `update` — o texto vem de regras em JS, por isso não por trigger); remoção por **trigger** `AFTER DELETE ON messages` (cobre `messagesRepo.delete` e os CASCADE de apagar sessão/chat). `insertAt` só desloca `seq`, que não fica no índice (vem do JOIN). Se o índice falhar ao abrir, `indexMessage` vira no-op e scope "all" responde erro; `chat_id` cai para a busca por substring.
- **Desempenho** (M-series, 50k mensagens sintéticas / 107 MB de JSON): criar o índice ≈ 3,5 s; scope "all" ≈ 2–50 ms para termos raros e ≈ 160–260 ms no pior caso (termo em ~96% das mensagens); manter o índice ≈ 0,05 ms por mensagem. Banco real (~2.900 mensagens): ≈ 0,2 s e +5 MB.
- Privacidade: qualquer chat com read_history habilitada lê todos os outros (não há permissão por chat).

## Subagentes em segundo plano, callbacks e conversa direta (`src/main/agent/subagents.ts`, runner)

- **Report**: cada execução de subsessão cujo resultado volta ao pai por callback (delegate em segundo plano, ou subsessão **retomada** por mensagem nova — usuário, `message_subagent` ou callback de um filho) é registrada (`ReportRegistry`). Ao terminar (concluiu / falhou / cancelada), salvo se reivindicada (`wait_subagents`/`message_subagent` com wait) ou apagada, o pai recebe uma mensagem `role: user` **sintética** (meta `{ kind:'subagent-callback', synthetic, subSessionId, callbackUpdate? }`): `[Subagente "<título>" (id …) concluiu]` / `— atualização após nova mensagem]` / `falhou]` (+ `delegateFailureText`) / `foi cancelado]` (+ parcial) / `não concluiu]\n(interrompido: o app foi fechado)`, seguida do texto final (cortado no teto). Entrega com a semântica da fila: pai rodando → próximo limite de passo (na ordem de término); pai ocioso → **acorda** (novo turno). Por isso o padrão orientado nas descrições das tools (`delegate_task`, `check_subagents`, `wait_subagents`) e no prompt de tools é: sem mais nada a fazer, o agente **encerra o turno** em vez de esperar — `wait_subagents` só quando o próximo passo do mesmo turno depende do resultado; nunca consultar `check_subagents` em loop.
- **Subagente com filhos pendentes**: ao encerrar um turno com filhos em segundo plano ainda rodando, **dorme** (status `waiting`, "aguardando subagentes") até chegar mensagem/callback na fila; só quando encerra um turno sem pendentes o resultado sobe (resultado do delegate bloqueante ou callback). Profundidade máxima continua 2.
- **Fila em todas as profundidades**: subsessões recebem mensagens (usuário, pai, callbacks); `agent.send` aceita subsessões (rodando/dormindo → fila; ⚡ interrompe só aquele subagente; ociosa/concluída → retoma; se o pai ainda espera um delegate bloqueante, a mensagem só faz parte da execução e a resposta final é o resultado da tool).
- **Parar**: Parar/⚡ na principal não derrubam subagentes em segundo plano (o loop deles não herda o signal); delegates bloqueantes continuam em cascata. Parar num subagente (banner) ou `cancel_subagent` para a subárvore toda (callbacks dos descendentes só registrados nos pais, sem acordá-los; o da raiz segue normal). "Parar todos os subagentes" (`agent.stopSubagents`). Apagar chat/mensagem do delegate: sem callbacks. Fechar o app: subagentes que reportariam por callback e ainda rodam deixam no pai "(interrompido: o app foi fechado)" sem acordá-lo (também na inicialização, após fechamento abrupto: sessões `running`/`waiting` → `interrupted`).
- UI: card do delegate com selo "em segundo plano" + status ao vivo + "Abrir subsessão"; callbacks como card compacto ("Subagente X concluiu", resultado recolhível, (i) com o texto exato, "Abrir subsessão"); subsessão com composer e banner "Conversando com o subagente <título> · as respostas dele voltam ao agente <pai>" (+ Parar); mensagens no subagente: "Você" vs "Agente pai", cada uma com (i); seletor de sessão em árvore agrupada sob o pai, rolável, recolhível, com contagem por status e "Parar todos os subagentes"; sidebar mostra o chat ocupado enquanto qualquer subagente roda. Pedidos de aprovação e falhas de subagentes: ver "Aprovações → Fila acima do composer".

## Runner / fila / interrupção (`src/main/agent/`)

Loop por sessão: `build → stream → persistir assistant → executar tool_calls sequencialmente → persistir tool msgs → [drenar fila] → repetir` até o assistente responder sem tool calls.

- **Fila**: `agent.send` com sessão rodando → `QueuedMessage` (memória, por sessão; `meta` opcional para mensagens de outro chat/pai/callbacks), evento `queue-updated`. Vale para qualquer profundidade. No próximo limite de passo (depois que os resultados das tools foram persistidos e antes da próxima chamada, OU quando o assistente termina o turno) todas as mensagens da fila são anexadas como mensagens `user` (meta.kind `queued`) e o loop continua imediatamente.
- **⚡ forceSend**: aborta o stream HTTP (AbortController) e as tools em andamento (kill do shell, nega approvals pendentes, aborta subsessões em cascata). Persiste o assistant parcial (se tem conteúdo; `meta.interrupted=true`; tool_calls incompletas descartadas). Para cada tool_call sem resultado, adiciona msg `tool` sintética `"[Interrompido pelo usuário antes de concluir]"` (toolStatus `cancelled`) — mantém o pareamento tool_call/tool válido. Então anexa a mensagem do usuário (meta.kind `forced`) e continua o loop.
- **stop**: igual ao abort acima, sem injetar; sessão `idle`; a fila permanece (cada item mostra ⚡ = enviar agora).
- Erros: status `error`, evento `error`; o usuário pode mandar nova mensagem ou `regenerate`.
- Título do chat: primeira mensagem do usuário truncada (~50 chars). Sem chamadas extras ao modelo.

## Markdown (renderer)

`components/chat/Markdown.tsx`: react-markdown + remark-gfm + **remark-math** → **rehype-katex** → rehype-highlight (KaTeX antes do highlight). O texto passa antes por dois pré-processamentos puros (testados em `e2e/markdown.test.ts`, parte do `npm run test:unit`):

- **Cercas aninhadas** (`lib/fences.ts`, `normalizeFences`): um bloco cercado que contém outros com a mesma cerca (README em ` ```markdown ` com ` ```python ` dentro) tem a cerca **externa** (abertura + fechamento) reescrita com mais crases/tis que a maior interna, então o remark vê um bloco só; o rótulo é a linguagem externa e "Copiar" copia o conteúdo com as cercas internas intactas. Dentro de um bloco (caractere C, comprimento L) só cercas de C com ≥ L são estruturais: com info string abrem nível, nuas fecham o nível mais interno; uma nua na profundidade 0 é candidata a fechar o externo. Entre as leituras possíveis (fechar na 1ª, 2ª… candidata ou não fechar — streaming) vence a de menor penalidade: cerca nua que abre seguida de linha em branco, que fecha seguida de texto colado, bloco vazio (abre+fecha coladas), abre colada após um fechamento, e mensagem terminando com cerca aberta (1,5). O resto da mensagem é avaliado junto (programação dinâmica sobre as linhas-cerca). Empate → a mais cedo (CommonMark); se a externa é `markdown`/`md`/`mdx`, a mais tarde. Cercas de 4+ que já englobam as internas, `~~~`, listas indentadas e CRLF são respeitados; citações (`> ```) não são tratadas.
- **Delimitadores de LaTeX** (`lib/math.ts`, `normalizeMath`), fora de blocos de código, código inline, blocos `$$` e escapes: `\[…\]` → `$$…$$` (em linhas próprias vira bloco de display com a indentação preservada; no meio da frase, inline) e `\(…\)` → `$…$`. `$…$` com um cifrão continua ligado (muitos modelos usam), mas só vale o par na regra do Pandoc — abertura com não-espaço à direita, fechamento com não-espaço à esquerda e sem dígito logo depois, na mesma linha; qualquer outro `$` vira `\$` (texto): "custa $5 e $10", "R$ 50" ficam texto. Streaming: `\[` sem fechamento no fim vira `$$` (a fórmula aparece aos poucos), `$$` aberto já vai até o fim, `$` sem par fica texto.
- KaTeX: `throwOnError:false` (via rehype-katex) com `errorColor` vermelho suave — TeX inválido mostra o fonte cru, nunca derruba a mensagem; durante o streaming o erro fica cinza (a fórmula final quase sempre está incompleta). Display rola na horizontal se for larga; cor herdada do texto. CSS em `components/chat/markdown-math.css` + `katex/dist/katex.min.css`; as fontes do KaTeX são empacotadas pelo Vite em `out/renderer/assets` (carregadas via `font-src 'self'`, sem rede). **`katex` fica em `^0.16`, a mesma versão que o rehype-katex usa** — a 0.19 renomeou classes (`sizing` → `katex-sizing`) e o CSS deixaria de casar com o HTML gerado (subscritos em tamanho cheio).

## Anexos (`src/shared/attachments.ts`, `src/main/attachments.ts`)

Enviar arquivos aos modelos que os aceitam — imagens, PDF, áudio e arquivos de texto/código.

- **Entrada (composer)**: botão 📎 "Anexar arquivos" (diálogo nativo via `attachments.pick`; o main lê os caminhos), **arrastar** arquivos para qualquer ponto do chat (overlay "Solte para anexar") e **colar** imagens (`attachments.add` com os bytes; imagem colada vira `colado-HHMMSS.png`). Cada arquivo vai na hora para o store e vira um chip acima do textarea (miniatura para imagens, ícone + nome + tamanho para os demais, X remove, (i) explica o envio). Pode enviar só anexos (texto vazio).
- **Limites** (`ATTACHMENT_LIMITS` em `src/shared/limits.ts`): 20 MB por arquivo, 10 anexos e 50 MB por mensagem, 200.000 caracteres por arquivo de texto (o resto é cortado com `[… arquivo cortado: mostrando N de M caracteres]`). Erros legíveis em pt-BR (tamanho, tipo não suportado, arquivo vazio).
- **Tipos** (`classifyAttachment`, por extensão/mime): imagem `png/jpg/webp/gif`; PDF; áudio `wav/mp3`; texto = extensões/mimes de texto e código, ou qualquer arquivo desconhecido que seja UTF-8 válido sem NUL. Outros binários (zip, docx, vídeo, bmp…) → "Tipo não suportado".
- **Capacidades**: `ModelInfo.inputModalities` vem de `architecture.input_modalities` do `/models`. Imagem exige `image`, PDF `file`, áudio `audio`; texto funciona com qualquer modelo. Sem a modalidade → aviso inline "Este modelo não aceita imagens" (modalidades desconhecidas, ex.: provider não-OpenRouter → "Não sei se este modelo aceita…", assume só texto); Enter não envia — só o botão **"Enviar mesmo assim"** (confirmação explícita). PDF no OpenRouter num modelo sem `file`: sem aviso — o OpenRouter extrai o texto do PDF (plugin file-parser) para qualquer modelo; o (i) do chip explica.
- **Codificação** (OpenAI-compatible / OpenRouter), um part por anexo, **anexos antes do texto** (`content: [...anexos, { type: 'text', text }]`; Anthropic recomenda imagens antes do texto, e o breakpoint de cache no último text part cobre a mensagem inteira):
  - imagem → `{ type: 'image_url', image_url: { url: 'data:<mime>;base64,…' } }`
  - PDF → `{ type: 'file', file: { filename, file_data: 'data:application/pdf;base64,…' } }`
  - áudio → `{ type: 'input_audio', input_audio: { data: '<base64>', format: 'wav' | 'mp3' } }`
  - texto → `{ type: 'text', text: '<file name="…">\n…\n</file>' }` (nome com `& " < >` escapados)
- **Persistência / caching**: o `message_json` nunca guarda base64. Os bytes ficam em `userData/attachments/<sha256>.<ext>` (content-addressed: mesmo arquivo = mesmo nome, dedup; escrita atômica tmp + rename). O part persistido é o formato do fio com uma referência no lugar do base64 — `{ type: 'image_url', image_url: { url: 'clearchat-attachment://<sha256>.png' }, _attachment: { name, mime, size, kind, file } }` (idem `file.file_data` / `input_audio.data`); arquivos de texto ficam inline (já no formato enviado) com `_attachment`. O tipo de part é decidido no envio e fica gravado no histórico. `buildRequest` chama `expandAttachments` **na cópia** (depois de `sanitizeHistory`, antes dos breakpoints): referência → data URL/base64 dos bytes do arquivo, e todo `_attachment` é removido — mesmos arquivos ⇒ mesmos bytes em toda request (o cache de prefixo funciona; leitura com cache LRU em memória). Mensagens sem anexos continuam string, idênticas.
- **cache_control**: continua no último text part da mensagem marcada; mensagem só com anexos (sem texto) recebe o breakpoint no último part (imagem/arquivo/áudio) — aceito via OpenRouter por Anthropic, OpenAI e Gemini (verificado).
- **Arquivo ausente** no disco → `buildRequest` lança `Anexo não encontrado no disco: "nome" (caminho). Apague a mensagem que contém esse anexo para continuar a conversa.` — vira o erro persistido do turno / erro no "Ver request", nunca crash. Na UI a miniatura mostra "arquivo ausente".
- **Preview** (`previewRequest`): mostra a estrutura expandida com o base64 encurtado (`data:image/png;base64,iVBORw0KGgoAAAANSUhEUgAA…(812 KB)`, `truncateBodyForPreview`) e `notes` ("Base64 de N anexos encurtado nesta visualização…") exibidas acima do Body.
- **Renderer**: miniaturas servidas pelo protocolo `clearchat-attachment://` (registrado como privilegiado no main; só lê nomes `^[0-9a-f]{64}(\.[a-z0-9]+)?$` do store; o CSP inclui o esquema em `img-src`/`media-src`). Mensagem do usuário: anexos acima do balão — imagens clicáveis (lightbox, Esc fecha), chips de arquivo com nome/tamanho, arquivos de texto com "Ver conteúdo" (prévia expansível) — cada um com (i) exato (part, tamanho → base64, "enviado em base64 em toda request enquanto estiver no histórico — conta tokens e é cacheável"). A fila mostra 📎 com os nomes.
- **Fila / ⚡ / edição**: `QueuedMessage.attachments` — a mensagem enfileirada leva os anexos e entra com eles no próximo passo (`kind: 'queued'`) ou no ⚡ (`kind: 'forced'`). `messages.update` (editar) preserva os parts de anexo: `withText` troca só o texto digitado.
- **Histórico em texto**: `contentText` ignora parts de anexo (copiar, editar, título — sem texto, o título vira o nome dos anexos). Compactação: o modo `full` reenvia os anexos (prefixo em cache); `trimmed`/`tail` trocam imagem/PDF/áudio por `[imagem: nome]` / `[PDF: nome]` / `[áudio: nome]` e encurtam arquivos de texto; o prompt de compactação pede para citar anexos assim e descrever o conteúdo relevante.
- **read_file de imagem/PDF** usa o mesmo store/referências/expansão (mensagem `tool` com parts — ver Tools → read_file).
- **GC** (no início, antes da janela): apaga do store os arquivos que nenhuma mensagem referencia — `message_json` **ou `meta_json`** (`LIKE '%clearchat-attachment://%'` + regex; o `meta_json` guarda as imagens do questionário em `meta.askUser`). Só nomes no formato do store (e temporários `.tmp-<uuid>`), só arquivos regulares e mais velhos que 1 h (anexos recém-escolhidos e ainda não enviados ficam; o dedup renova o mtime). Apagar chat/mensagem deixa órfãos até o próximo início.

## Questionário (`ask_user`, `src/shared/askUser.ts`, `src/main/askUserImages.ts`, `src/main/agent/questions.ts`, runner, `components/chat/AskUser.tsx`)

O agente principal faz um questionário de múltipla escolha; a UI troca o campo de texto do composer por um formulário passo a passo e as respostas voltam como resultado da tool.

- **Esquema**: `questions` 1–5; cada uma `{ title (≤ 200), description? (≤ 1000), multiple? (padrão false), options 1–5 }`; opção `{ title (≤ 200), icon?, description? (≤ 1000), image?, help? (texto ≤ 4000) }`. "Outro" é sempre adicionada pela UI (não conta). `parseAskUserArgs` valida e devolve erros legíveis em pt-BR (lista com até 12, ex. "Máximo de 5 opções por pergunta (pergunta 2 tem 7)") — nada é mostrado se inválido. Campos opcionais vazios são descartados (não aparecem na UI). Tolera `questions`/`options` como string JSON e opção como string.
- **Disponibilidade**: só depth 0 (`availableTools`; o runner também recusa em subagente). Fora de `CONFIRM_TOOLS` e nunca passa pelo gate de aprovações/Smart-Approve (rota `run` fixa no runner). Habilitada por padrão em chats novos (como as demais).
- **Formas de `icon`** (`classifyIcon`, nessa ordem): começa com `<svg` → SVG inline; `http(s)://` → URL; `data:` → data URL; contém `/` ou `\` ou termina em `.png/.jpg/.jpeg/.webp/.gif/.svg` → arquivo local; kebab-case `[a-z0-9-]+` → ícone lucide; senão → texto (emoji, ≤ 16 caracteres). `image` = SVG inline / URL / data URL / caminho. `help` (`classifyHelp`): SVG inline, URL/data URL sem espaços ou caminho de uma palavra com extensão de imagem → imagem; o resto é **texto** (monoespaçado, preserva espaços/ASCII art).
- **Imagens (segurança)** — resolvidas quando a tool executa, antes de mostrar o questionário (`resolveAskUserQuestions`): URL → `fetch` no **main** (timeout 15 s, até 5 MB lidos em streaming, `content-type` image/png|jpeg|webp|gif|svg+xml **e** bytes conferidos por assinatura); caminho → relativo ao raiz, com `confineToRoot` precisa ficar dentro dele após realpath (`assertInsideRoot`, mesma regra das tools de arquivo), ≤ 5 MB, bytes conferidos; SVG inline (≤ 200 KB) / data URL → arquivo. Tudo vai para o store de anexos (`saveStoreFile`, content-addressed, `.svg` incluso) e chega à UI como `clearchat-attachment://<sha>.<ext>` — o protocolo serve `image/svg+xml` e o CSP já tem o esquema em `img-src` (nada de `http:`). Exibição **sempre via `<img>`** (scripts de SVG nunca executam). Falha de uma imagem → ela só não aparece; nota no resultado ao modelo, ex. `[imagem da opção 2 da pergunta 1 indisponível: HTTP 404]` / `[ícone da opção 5 da pergunta 1 indisponível: caminho fora do diretório raiz (acesso negado)]`.
- **Ícones lucide**: `DynamicIcon` de `lucide-react/dynamic` (cada ícone é um chunk carregado sob demanda pelo Vite — mesmo origin, CSP ok); nome fora de `iconNames` → sem ícone. Emoji → texto. Imagem → `<img>` 20 px, `object-contain`, cantos arredondados; quebrada → some.
- **Pendente** (`questions.ts`, análogo a `approvals.ts`): `QuestionRequest` em memória, evento `question-requested`, sessão **`awaiting_input`** ("Aguardando sua resposta" no composer, ponto âmbar na sidebar e no seletor de sessões, chip "Pergunta pendente" no header quando o chat não está na tela; `isBusy` = true; `list_chats`/`check_subagents` mostram "aguardando resposta do usuário"). Mensagens que chegarem nesse meio-tempo (callbacks de subagentes, mensagens de outros chats) entram na **fila** normal e são entregues no próximo limite de passo após a resposta; o campo de texto fica oculto, mas os chips da fila (com ⚡) continuam visíveis.
- **Respostas**: `questions.answer(id, answers)` valida (`validateAnswers`: todas respondidas, índices válidos, single = uma resposta só, "Outro" ≤ 4000 e não vazio). Resultado (toolStatus `ok`, cortado em `maxToolOutputChars`):
  ```
  Respostas do usuário:
  1. Qual banco de dados? → PostgreSQL
  2. Quais recursos? → Cache, Filas, Outro: "notificações push"
  3. Hospedagem? → Outro: "servidor próprio na Hetzner"
  ```
  (+ linha em branco e as notas de imagens, se houver). `meta.askUser = { questions, outcome: 'answered', answers, notes? }` para o card.
- **Cancelar** (Esc no formulário/"Cancelar" → `questions.cancel` = `agent.stop`; botão Parar; `api.agent.stop`): o abort resolve a pendência e o resultado é `[O usuário não respondeu ao questionário]` (toolStatus `cancelled`, `meta.askUser.outcome 'cancelled'`); o loop para — turno termina, sessão `idle`, **sem nova chamada ao modelo**; a fila é mantida. A próxima entrada (mensagem do usuário ou callback) inicia o turno normalmente e o modelo vê `assistant(tool_calls ask_user) → tool("não respondeu") → user(nova mensagem)` — par válido (`sanitizeHistory` mantém). **⚡** durante o questionário = cancelamento + a mensagem forçada (o loop continua com ela; status volta a `running`).
- **App fechado** com questionário pendente: `shutdownRunner` grava `[não respondido: o app foi fechado]` (com `meta.askUser.outcome 'app-closed'`); fechamento abrupto → na inicialização a sessão vira `interrupted` e `repairTail(…, 'app-closed')` grava o mesmo texto para o tool_call de `ask_user` sem resultado.
- **GC**: as URLs do store das imagens resolvidas ficam em `meta_json` (`meta.askUser`); `referencedFilesInDb` lê `message_json` **e** `meta_json`, então elas não são apagadas.

"Outro" sempre por último (abre um campo de texto; em `multiple` combina com as marcadas; em single substitui a seleção). Teclas: 1–5 opções, 6 (= nº de opções + 1) Outro, Enter avança/envia, ←/→ navegam, Esc cancela (Esc num popover de ajuda fecha só o popover). **Não dá para pular**: Próximo/Enviar só habilitam com resposta (opção ou "Outro" com texto); para não responder, o usuário escreve o motivo em "Outro".
- **UI — card** (ToolCard `ask_user`, ícone de balão com "?"): pendente → "aguardando sua resposta" + lista de perguntas; respondido → pergunta → resposta(s) (chips com ícones; "Outro: …"); cancelado → "Não respondido" (+ "o app foi fechado"). Expandido: argumentos e o texto exato enviado ao modelo com (i), como os outros cards. Modo sem tools nativas: funciona, mas o card não tem o `meta.askUser` (só o texto).
- **Testes**: `e2e/askUser.test.ts` (validação, classificação, respostas, texto, depth, pareamento após cancelar, imagens com servidor HTTP local / fora do raiz / svg inline, GC via `meta_json`) e `e2e/ask-user.spec.ts` (UI real com provedor falso: responder com teclado/Outro/Voltar, Esc e Parar cancelam sem nova chamada ao modelo, próxima mensagem vê o "não respondeu").


## Falha de conexão (nova tentativa) — `src/shared/network.ts`, `src/main/agent/retries.ts`, runner, `components/chat/RetryCard.tsx`

Quando a chamada ao modelo do loop (`step`) falha por **erro de rede** (Wi-Fi caiu, notebook suspenso, DNS, conexão cortada no meio do stream), o turno não falha: a sessão espera a decisão do usuário num card bloqueante.
- **Classificação** (`isConnectionFailure(e)`): `isNetworkError` (regex: `terminated`, `fetch failed`, `Falha de rede`, `other side closed`, `socket hang up`, `ECONNRESET`/`ECONNREFUSED`/`ENOTFOUND`/`EAI_AGAIN`/`ETIMEDOUT`/`ENETUNREACH`/`ENETDOWN`/`EHOSTUNREACH`/`EPIPE`, `UND_ERR_*`, `network error|changed`, `Sem resposta do provider` — watchdog de 120 s) sobre a mensagem **e as causas** (`cause.message`/`cause.code`). Nunca é rede: `LlmHttpError` (qualquer HTTP 4xx/5xx/429, objeto com `status`), texto começando por `Erro HTTP` ou contendo `Erro do provider` (erro vindo do provider no stream). `isNetworkError` mudou para `@shared/network`; `tools/models.ts` reexporta. Fora de escopo (como antes): juiz do Smart-Approve, compactação, list_models/teste de provider.
- **Pendente** (`retries.ts`, análogo a `questions.ts`): `RetryRequest { id, chatId, sessionId, error (curto: mensagem + causas, ≤ 300), model, providerName?, createdAt }` em memória, eventos `retry-requested`/`retry-resolved`, IPC `retries.retry(id)` / `retries.cancel(id)` / `retries.pending()`. Sessão **`awaiting_retry`** (isBusy; "Aguardando sua decisão (falha de conexão)" no composer; ponto âmbar na sidebar e no seletor de sessões, contagem "falha de conexão"; `list_chats`/`check_subagents`: "aguardando decisão do usuário (falha de conexão)"). Mensagens/callbacks que chegarem enquanto o card está aberto vão para a **fila** normal (chips com ⚡ continuam visíveis).
- **Parcial descartado**: ao detectar a falha o draft é zerado (`draft: null`) e nada do assistant parcial é persistido.
- **Tentar de novo**: a request é reconstruída do histórico (inalterado) e a chamada refeita do zero (`callWithNetworkRetry`); falhou de novo por rede → card de novo. Status volta a `running`.
- **Cancelar** (botão/Esc), **Parar** (quadrado/`agent.stop`) com o card aberto: o turno termina como erro, exatamente como antes do card — `appendError` (mensagem `meta.kind:'error'` com o erro original), evento `error`, status `error`, sem nova chamada. **⚡** com o card aberto: o mesmo erro é persistido e em seguida entra a mensagem forçada (loop continua).
- **Subagentes**: o card aparece na **subsessão** (que fica `awaiting_retry`; não falha nem devolve erro ao pai). Delegate bloqueante → o pai continua `running` esperando o resultado; segundo plano → nada muda para o pai até resolver. No pai: o card do `delegate_task` mostra "Subagente aguardando sua decisão (falha de conexão)" + erro + "Abrir subsessão"; no topo, chip **"Subagente aguardando decisão"** (`RetryIndicator`, como "Pergunta pendente"; "Falha de conexão" para outra sessão principal) que abre a sessão do card; a sidebar marca o chat. Parar o pai em cascata com o card aberto no subagente → o delegate devolve `[Interrompido pelo usuário antes de concluir]` (cancelled). Cancelar no subagente → falha como antes (`delegateFailureText` de rede agora diz que o usuário optou por não tentar de novo).
- **App fechado** com o card aberto: `shutdownRunner` persiste o erro `Falha de conexão com o provedor: <erro> (interrompido: o app foi fechado)` e marca a sessão `error`; fechamento abrupto → na inicialização `sessionsRepo.markStaleRetry()` muda `awaiting_retry` → `error` e `initRunner` grava `Falha de conexão com o provedor (interrompido: o app foi fechado)` (+ `repairTail`).
- **UI** (`RetryForm`, no lugar do campo de texto do composer, como o questionário; anexos/enviar escondidos, Parar continua): ícone Wi-Fi cortado, "Falha de conexão com o provedor", erro curto (mono), "<Provedor> · <modelo> · a resposta parcial foi descartada…", botões **Tentar de novo** (focado; Enter) e **Cancelar** (Esc; Enter com ele focado). Mock: `VITE_CLEAR_MOCK=retry` (principal) / `retry-sub` (subagente).
- **Testes**: `e2e/networkRetry.test.ts` (classificação rede × provider; runner real com stub de `electron`, SQLite temporário e provedor falso que corta o socket: retry descarta o parcial e entrega a fila depois; Cancelar = erro; HTTP 500 sem card; Parar e ⚡; subagente bloqueante esperando; inicialização e encerramento) e `e2e/network-retry.spec.ts` (`npm run test:e2e:retry`: UI real — card, Enter/Esc, Parar, subagente com chip/card no pai → subsessão → retry).

## Memória (contrato — `src/shared/memory.ts`, `src/main/memory/`, runner, UI)

Memória modular: cada **coleção** (criada pelo usuário, global) pertence a **uma categoria** da taxonomia fixa e contém **memórias** dessa categoria — ex.: "Padrão" em cada categoria, "Projeto TCC" em Áreas. Chats e personas **ativam** coleções (várias por categoria, para leitura), escolhem **no máximo uma coleção de escrita por categoria** e podem desligar categorias inteiras; criação e edição de conteúdo é global (Configurações → Memórias). A memória é **só** isso: não existe memória "do chat" — o contexto do chat já é a memória dele.

### Taxonomia fixa (instruções padronizadas, na descrição de `memory_write`)
`profile` (quem é o usuário) · `topics` (hábitos e interesses recorrentes) · `areas` (frentes ativas: projetos, tarefas em andamento) · `people` (pessoas — e animais) · `preferences` (como o usuário quer que o chat se comporte). Rótulos pt-BR: Perfil, Tópicos, Áreas, Pessoas, Preferências.

### Dados (SQLite — `src/main/memory/schema.ts`, `ensureMemorySchema` idempotente, chamado em `db.ts`)
```sql
memory_collections(id TEXT PK /* randomUUID */, category TEXT /* fixa */, name TEXT, description TEXT, icon TEXT NULL,
                   scope TEXT /* legado: sempre 'shared' */, chat_id TEXT NULL /* legado: sempre NULL */, created_at, updated_at)
memories(id TEXT PK /* 'm' + 7 base36 — curto: vai no índice de toda request */, collection_id TEXT REFERENCES memory_collections ON DELETE CASCADE,
         category TEXT /* = da coleção */, title TEXT, slug TEXT UNIQUE, summary TEXT, facts_json TEXT /* string[] */, pinned INTEGER,
         created_at, updated_at, updated_by_chat_id TEXT NULL, updated_by TEXT /* 'model' | 'extraction' | 'user' */,
         supersedes_id TEXT NULL /* memory_rewrite; sem FK — trigger zera quando a original é apagada */)
memories_fts USING fts5(title, summary, facts, memory_id UNINDEXED, tokenize='unicode61 remove_diacritics 2')  -- triggers ai/au/ad (cobrem CASCADE)
sessions.memory_json TEXT NULL  -- { snapshot?: { at, key, index }, lastExtractedSeq? }
```
- **Repositório** (`src/main/memory/store.ts`, `MemoryStore(conn, { onChange })`; erros de regra = `MemoryError` com texto legível): CRUD de coleções (categoria imutável; apagar coleção apaga as memórias) e memórias (categoria vem da coleção; **mover só para coleção da mesma categoria**). Cada mudança chama `onChange` → evento `memory-changed`. As leituras de coleção filtram `scope = 'shared'` (nada cria nem lê coleções de chat).
- **Migração da antiga "memória do chat"** (`removeChatMemory`, chamada por `ensureMemorySchema` a cada abertura; idempotente — depois da 1ª não acha nada): apaga as coleções `scope='chat'` e as memórias delas (só serviam ao chat dono; o FTS sai por trigger, `supersedes_id` que apontava para elas é zerado) e tira `memory.chatMemory` do `config_json` de chats e personas; loga `memória do chat removida: N coleções e M memórias apagadas; chatMemory retirado de X chats e Y personas` quando algo muda. As colunas `scope`/`chat_id` ficam (legado; derrubá-las exigiria recriar a tabela).
- **Limites** (`MEMORY_LIMITS` em `limits.ts`): título ≤ 80, resumo ≤ 160, tópico ≤ 200, ≤ 15 tópicos (erro: `Título longo demais (81/80 caracteres)…`, `Tópicos demais (16/15)…`); nome de coleção ≤ 60, descrição ≤ 300. Espaços colapsados, tópicos vazios/duplicados (sem caixa/acento) removidos.
- **Slug** = título sem acentos/pontuação com hífens (≤ 60), **único global** (`-2`, `-3`…), **estável** (não muda ao renomear: links `[[slug]]` nos tópicos continuam valendo). `findMemory` aceita id, slug ou `[[slug]]`.
- **Busca**: FTS5 com prefixo por palavra (`"pal"*` OR …), bm25 título 5 · resumo 2 · tópicos 1; trecho = 1º tópico (ou resumo) com a palavra. Sem FTS5 → LIKE.
- **Semelhança** (antes de criar): mesma coleção, mesmo slug-base, ou FTS no título + palavras significativas (sem stopwords) com sobreposição ≥ 60% da menor lista (ex.: "Projeto do TCC" × "TCC").

### Config (em `ChatConfig.memory?`, persona via `PRESET_FIELDS`; chat herda da persona como hoje)
```ts
interface MemoryConfig {
  enabled: boolean                          // desligado → NADA de memória vai para a API (sem índice, sem help, sem tools)
  collections: string[]                     // coleções ativas para leitura (várias por categoria)
  writeTo: Partial<Record<MemoryCategory, string | null>> // coleção de escrita por categoria (uma das ativas); null = não grava
  categories: MemoryCategory[]              // categorias ligadas (padrão: todas)
  helpPrompt: { enabled: boolean; text: string | null }       // null = padrão; anexado ao system prompt
  extraction: { auto: boolean; prompt: string | null; providerId: string | null; model: string | null } // null = modelo do chat
  subagents: boolean                        // memory_search/memory_read para subagentes (nunca escrita, nunca índice)
}
```
- `normalizeMemoryConfig` (shared) completa/limpa qualquer valor salvo (ausente = `defaultMemoryConfig()` = desligada) e descarta campos legados (ex.: `chatMemory`). **Persona**: `sanitizePresetConfig` grava `memory` normalizada; `applyPreset` a aplica como os demais campos. Herança = snapshot na criação do chat.
- **Resolução** (`activeMemory(store, chat, session)` em `src/main/memory/config.ts`): categorias ligadas (`enabled` ? `categories` : nenhuma); coleções ativas por categoria = selecionadas que existem e estão em categoria ligada; `writeTo[cat]` só vale se for uma das ativas daquela categoria (senão null); `canWrite` = algum `writeTo` válido.
- **Regra de envio**: memória ativa ⇔ `enabled` **e** ao menos uma coleção ativa numa categoria ligada; senão → nenhum bloco, nenhuma tool. Tools: principal → `memory_search`, `memory_read` + (`canWrite` ? `memory_write`, `memory_rewrite`, `memory_delete`); subagente → `memory_search`/`memory_read` só com `subagents` (e memória ativa no chat). As tools de memória **não** entram em `TOOL_NAMES`/`enabledTools` (`MEMORY_TOOL_NAMES` em `tools.ts`); `availableTools` as acrescenta no fim (ordem fixa). Definições estáticas (sem dados da sessão) → prefixo estável.

### Envio à API (controle total: tudo com (i))
- **Ordem do system prompt** (`systemContent`): system prompt → `<environment>` → **índice** → **help** → texto das tools (modo texto). Fontes registradas pelo main (`setMemorySources` em `request.ts`; sem registro = nada, testes puros). `previewRequest` ("Ver request") e `memory.preview` → `{ active, index, help, tools, snapshotAt }` mostram o mesmo.
- **Índice** (`src/main/memory/render.ts`): `<memory>` + cabeçalho (congelado; memory_read/memory_search; escrita × leitura) → `## Rótulo (categoria: o que guarda)` (só categorias com coleção ativa) → `### Coleção — escrita|leitura` + descrição → `- id · título — resumo`; fixadas com os tópicos numerados; coleção vazia `(vazia)`. Ordem: fixadas, depois mais recentes. **Substituídas ocultas** onde a substituta (supersedes_id) também está ativa. **Teto** `MEMORY_LIMITS.indexMaxChars` (12.000): ficam fixadas + mais recentes que cabem, `(+N não listadas)` por coleção e `[N memórias fora do índice por tamanho — use memory_search…]`.
- **Congelado por sessão** (`MemoryService`, `src/main/memory/service.ts`): o runner chama `ensureSnapshot` antes de cada chamada da principal — sem snapshot válido, grava `{ at, key, index }` em `sessions.memory_json`. `key` = coleções ativas + escrita + categorias (memórias novas NÃO mudam a chave → o cache não quebra; mudar a config muda → índice novo). Renovado em: sessão nova, compactação (`afterCompaction` limpa; o próximo request tira outro), `memory.refreshSnapshot` ("Atualizar memória"). Antes do 1º request o preview mostra o índice atual com `snapshotAt: null`. O que o modelo grava durante a sessão chega pelos resultados das tools.
- **Help prompt** (se ligado): `text ?? DEFAULT_MEMORY_HELP_PROMPT` (`defaults.ts`).
- **Subagentes**: nunca recebem índice nem help; só `memory_search`/`memory_read` se `subagents` (e memória ligada no chat).

### Tools (`src/main/tools/memory.ts`, `runMemoryTool(name, args, { store, am, by })` — mesmas regras para agente e extração; nunca lança: erro de regra/limite → resultado `Erro: …`)
- Aprovações: itens `memory_write`, `memory_rewrite`, `memory_delete` (padrão "Sempre permitir"; também Smart-Approve e "Perguntar"). Busca e leitura nunca perguntam. A mensagem tool leva `meta.memoryChanges` (`{ op, memoryId, title, collectionId }[]`).
- `memory_search { query, category?, collection? (id ou nome de coleção ATIVA), limit? (10, máx. 30) }` → `[busca na memória: "q" · N resultados]` + `- id · Categoria · Coleção (escrita|leitura) · título — resumo` + `trecho:`. Só coleções ativas; substituídas ocultas.
- `memory_read { ids[] (até 20; id ou slug) }` → cabeçalho, categoria, coleção, `[[slug]]`, atualização (data, por modelo/extração/usuário), `substitui:`, resumo, tópicos numerados; fora das ativas → "(não está numa coleção ativa deste chat)"; substituída → aponta a substituta.
- `memory_write { category?, id?, title?, summary?, ops?: [{ op: 'add'|'remove'|'replace', fact, with? }], force_new? }` → **sem id cria** (category + title obrigatórios; só `add`) na coleção de escrita da categoria (`writeTo[category]`). Sem coleção de escrita na categoria → `Erro: Sem coleção de escrita para Perfil (profile) neste chat — o usuário escolhe nas configurações de memória do chat.` (nada é criado). Categoria desligada → erro. **Semelhante** na coleção → NÃO cria: `Nada foi criado: já existe memória parecida…` + candidatas (id, título, tópicos) pedindo `id` (ou `force_new: true` se for outro assunto). **Com id atualiza** (só graváveis; só leitura → "use memory_rewrite"; a categoria não muda). `remove`/`replace` acham o tópico por `#n`, texto exato (sem caixa/acento) ou trecho único; não achou/ambíguo → erro com a lista atual. O resultado mostra a memória final (id, título, tópicos).
- `memory_rewrite { id, title?, summary?, facts? (lista completa nova) | ops? }` → origem em coleção ativa **só de leitura**: cria na coleção de escrita da categoria uma cópia atualizada com `supersedes_id = id` (herda título/resumo/fixada se omitidos); sem coleção de escrita na categoria → o mesmo erro de `memory_write`. Já existe substituta dessa origem na coleção de destino → atualiza ela. Origem gravável → update no lugar.
- `memory_delete { id }` → só graváveis.
- As tools de escrita só são oferecidas se ao menos uma categoria tiver coleção de escrita válida (`canWrite`). Descrições curtas, com a taxonomia e a regra de discrepância (`MEMORY_TOOL_DEFINITIONS` em `tools.ts`).

### Extração (`src/main/memory/extraction.ts`, `extractNow`/`afterCompaction` em `src/main/memory/index.ts`)
- **Gatilhos**: `memory.extractNow(sessionId)` ("Extrair memórias agora"; só sessão principal; uma por sessão de cada vez — chamada concorrente recebe a mesma promise) e, com `extraction.auto`, **após toda compactação bem-sucedida** da principal (em segundo plano; o turno não espera).
- **Request separada** (nunca no histórico), ao provedor/modelo de `extraction` (`model` null → modelo da sessão/chat; `providerId` só vale com `model`), no formato do adaptador (OpenAI-compatible ou Anthropic), assinatura de app do chat, **tools nativas** = só as de escrita disponíveis. Mensagens: system = `extraction.prompt ?? DEFAULT_MEMORY_EXTRACTION_PROMPT`; user = **índice completo** das coleções ativas (todos os tópicos, teto 40.000) + `<conversation>` + instrução final.
- **Conversa**: só o histórico ativo (da última fronteira); mensagens com `seq > lastExtractedSeq` ("Usuário:", "Assistente:" com as chamadas resumidas, resultados de tool encurtados, sintéticas como "[app]"); a fronteira de compactação entra como `[Resumo da conversa anterior]` (texto limpo) se resumir algo não extraído — ou sempre, quando o gatilho é a compactação (= resumo + mensagens recentes). Corte pelo início em 60.000 caracteres. Sem fala nova → nada é enviado: `extractNow` devolve `error: 'Nada novo na conversa desde a última extração.'` e não grava card.
- **Loop**: até `MEMORY_LIMITS.extractionMaxRounds` (4) requests; cada tool call roda com `runMemoryTool` (`updatedBy: 'extraction'`, mesmas regras; a extração não passa pelo gate de aprovação — foi o usuário que a disparou/ligou); resultados voltam como mensagens `tool`; para quando o modelo não chama mais tools.
- **Resultado**: `MemoryExtractionResult` (+ model, providerId, usage somado, request mascarada da 1ª chamada, trigger) persistido como mensagem `role: 'assistant'` "Extração de memórias: 2 criadas, 1 atualizada." com `meta: { synthetic: true, kind: 'memory-extraction', memoryExtraction }` — **só de exibição** (`isDisplayOnly` em `context.ts`, como `kind:'error'`): fora da API, do contexto, da compactação, do FTS, de `read_history`, do `repairTail`. Sucesso → `lastExtractedSeq` = maior seq considerado. Erros (provedor, sem destino de escrita, memória inativa) → `result.error` no card; nunca quebram o chat.

## Skills (contrato — `src/shared/skills.ts`, `src/main/skills/`, `src/main/tools/skills.ts`, request, runner, UI)

Skills no formato **Agent Skills** da Anthropic / Claude Code (conferido em agentskills.io/specification e code.claude.com/docs/en/skills, 2026-10): uma skill é uma **pasta** com `SKILL.md` — frontmatter YAML entre linhas `---` + corpo markdown — e arquivos extras opcionais (`scripts/`, `references/`, `assets/`…). **Não há índice de skills no contexto**: com as skills ligadas vão um prompt de apoio (opcional) e três tools; o modelo descobre as skills com `list_skills`. Nenhuma criação/edição de skill pelo modelo.

### Formato e parse (`src/main/skills/parse.ts`, puro)
- `parseSkillMd(texto, nomeDaPasta)` → `{ meta, body, content, warnings, error? }`. Texto normalizado (BOM fora, CRLF/CR → LF) — `content` é o que vai ao modelo. YAML: o subconjunto usado nas skills (`parseYaml`): `chave: valor` simples / entre aspas (`"…"` com escapes, `'…'` com `''`) / multilinha dobrado, blocos `|` e `>`, listas (`- x` e `[a, b]`), um nível de mapa (`metadata:`), comentários `#`. Erro de YAML → skill inválida com a linha.
- **Inválida** (aparece nas Configurações com o erro; nunca é oferecida): sem frontmatter (1ª linha ≠ `---`), frontmatter não fechado, YAML ruim, `name` não textual, **sem `description`** (vazia conta) ou `SKILL.md` > 1 MB.
- **Avisos** (continua válida): sem `name` → usa o nome da pasta (como o Claude Code); `name` ≠ pasta; nome fora do padrão da spec (`a-z0-9` e hífens, sem hífen no início/fim nem duplo, ≤ 64); `description` > 1024; `compatibility` > 500.
- Campos conhecidos: `name`, `description`, `license`, `compatibility`, `allowed-tools` (texto ou lista → texto separado por espaço; **só informativo** — não altera aprovações), `metadata` (mapa). Os demais vão para `meta.other` (texto) — mostrados na UI e ignorados.

### Locais e descoberta (`src/main/skills/discovery.ts`, fs puro; settings em `src/main/skills/index.ts`)
- Setting global `skillsSettings` = `SkillsSettings { locations: { id, path, enabled }[]; projectSkills: boolean }` (`normalizeSkillsSettings`: ids únicos, caminhos não vazios e sem repetição; o id `project` é reservado). Padrão: `[{ id: 'default', path: '~/.claude/skills', enabled: true }]` (listada mesmo sem a pasta existir — "pasta não existe") + `projectSkills: true`. `~` é guardado e expandido ao escanear (`expandHome`).
- Cada local é uma pasta cujas **subpastas com `SKILL.md`** são skills (links de pasta seguidos; ocultas ignoradas; ≤ 500 por local) — ou a própria pasta, se tiver um `SKILL.md`. Skills de projeto: `<cwd do chat>/.claude/skills` (`projectLocation`), por último, só se `projectSkills` (e não duplicam um local já listado).
- **Precedência**: a ordem dos locais; nomes repetidos → vence a primeira ocorrência; as outras ganham `shadowedBy` (rótulo do local vencedor). `discoverSkills` escaneia todos os locais (inclusive desabilitados, para a UI) e devolve `SkillsDiscovery { locations: SkillLocationScan[]; skills }` — `skills` = efetivas (válidas, de locais habilitados, sem as sobrescritas). `counts` conta os arquivos (Configurações).
- **Cache**: parse por (mtime, tamanho) do `SKILL.md`; "Reescanear" (`discover({ rescan: true })`) limpa o cache e emite `skills-changed`. A listagem de pastas é refeita a cada descoberta (barata).
- `listSkillFiles(dir)`: recursivo, `SKILL.md` primeiro, pula `.git`/`node_modules`/`__pycache__`/`.venv` e pastas ocultas, não segue links de pasta; ≤ 500 arquivos, profundidade ≤ 6.

### Config (em `ChatConfig.skills?`, persona via `PRESET_FIELDS`; chat herda da persona como a memória)
```ts
interface SkillsConfig {
  enabled: boolean                                   // desligado → NADA de skills vai para a API (sem prompt, sem tools, sem lâmpada)
  disabled: string[]                                 // skills desligadas aqui (por nome); padrão = todas as efetivas
  supportPrompt: { enabled: boolean; text: string | null }   // padrão ligado; null = DEFAULT_SKILLS_SUPPORT_PROMPT (defaults.ts)
  subagents: boolean                                 // subagentes recebem as mesmas tools + prompt de apoio (padrão false)
}
```
- `normalizeSkillsConfig` (ausente = `defaultSkillsConfig()` = desligada). Skills ativas de um chat = `activeFromDiscovery(discover({ cwd }), cfg)` = efetivas − `disabled` (`activeSkillsFor`). Sessão: `skillsActiveFor(cfg, session)` = `enabled && (depth === 0 || subagents)`; subagentes usam o mesmo conjunto ativo do chat.

### Envio à API (controle total: tudo com (i))
- **Só a config decide** (`skillsActive` / `skillsSupportPrompt` em `request.ts`) — nunca as skills descobertas: definições e prompt **estáveis na sessão** (prefixo de cache), mesmo que skills apareçam/sumam.
- System prompt (`systemContent`): … → memória → **prompt de apoio** (`\n\n` + texto) → texto das tools.
- Tools: `SKILL_TOOL_NAMES = ['list_skills', 'skill_load', 'skill_read']` (fora de `TOOL_NAMES`/`enabledTools`, `SKILL_TOOL_DEFINITIONS` em `tools.ts`), acrescentadas por `availableTools` **depois** das de memória. A lista de skills nunca vai nas definições. Modo texto: entram no texto das tools como as demais.
- Só leitura → não são itens de aprovação (rodam direto; nem Smart-Approve). Scripts rodam pela tool `shell`/`process_start` com as aprovações normais. Sandbox (bwrap): as pastas das skills ativas da sessão (realpath, só as que existem e não estão dentro da raiz) entram como `--ro-bind` depois do `/tmp` privado e antes da raiz (`shellArgv(…, roBinds)` / `sandboxBinds`; o `/` já é somente leitura, mas skills sob `/tmp` ficariam escondidas).

### Tools (`src/main/tools/skills.ts`; registradas em `runLocalTool`; `ToolContext.skills` = skills ativas da sessão, resolvidas pelo runner; erros → `Erro: …`)
- `list_skills { query? }` → `[N skills disponíveis neste chat]` (ou `[K de N skills para "q"]`) + `- nome — descrição (local)` (descrição numa linha) + "Carregue a que se aplica com skill_load…". `query`: todos os termos no nome/descrição, sem acento/caixa. Corta no teto `maxToolOutputChars` com `[… mais N skills — refine com query]`. Nenhuma → orienta Configurações → Skills.
- `skill_load { name }` (nome exato; senão sem caixa; senão o nome da pasta) → `<skill name="…" path="<pasta absoluta>">\n<SKILL.md>\n</skill>` + `Pasta da skill: …` + `Arquivos (N):` (`caminho (tamanho)`, ≤ 1/3 do teto) + dica de `skill_read` e de rodar scripts com `shell` pelo caminho absoluto. SKILL.md maior que o que cabe → cortado em linha com `[… SKILL.md cortado: … leia o resto com skill_read {"name", "path": "SKILL.md", "offset": N}]`. Não encontrada → erro com os nomes disponíveis.
- `skill_read { name, path, offset?, limit? }` → `path` relativo à pasta da skill (absoluto aceito se dentro dela); **confinado por realpath** (`..`, absoluto de fora e links que escapam → `Erro: acesso negado — "…" fica fora da pasta da skill "x" (…)`), **independente de `confineToRoot`**. Leitura = `readFile` do `read_file` (mesmo formato, janelas e limites; imagem/PDF se o modelo ler) com a pasta da skill como base.

### Invocação manual (lâmpada do composer)
- Só com `skills.enabled` no chat. A lâmpada abre um picker com busca (↑/↓, Enter, Esc) entre as skills **ativas**; escolher adiciona um chip "Carregar skill X" (vários; removíveis; `store.pendingSkills[sessionId]`). Desligar as skills esconde os chips (nada é enviado).
- `agent.send(sessionId, text, attachments, skills)` → `runner.sendWithSkills`: lê cada `SKILL.md` **no envio** (`resolveManualSkills`: skills desligadas / inexistente ou desligada / falha de leitura → **erro legível e nada é enviado**; o composer devolve texto, anexos e chips) e monta `manualSkillPart` = `{ type: 'text', text: '<skill name="…" path="<pasta>">\n<SKILL.md normalizado>\n</skill>', _skill: { name, path, truncated? } }` (≤ 200.000 caracteres; acima, cortado com nota). Conteúdo da mensagem: `[...anexos, ...skills, { type:'text', text }]` (texto vazio permitido com skill). Fila e ⚡: os parts já lidos viajam em `QueuedMessage.skillParts`.
- Request: `expandAttachments` remove `_skill` (e `_attachment`) **na cópia** — o texto enviado é idêntico ao persistido; cache_control no último text part como sempre. `contentText` ignora parts de skill (título, copiar, editar — `withText` preserva o part); `messageSkills(msg)`. Compactação encurtada (`trimmed`/`tail`) troca por `[skill carregada: nome]`.
- UI: card "Skill carregada: X" acima do balão (SKILL.md · N caracteres, "Ver conteúdo enviado", link para Configurações → Skills, (i) com o texto exato); a fila mostra 💡 com os nomes.
